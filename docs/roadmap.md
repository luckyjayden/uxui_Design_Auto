# 프로젝트 로드맵: AI UX 설계 자동화 시스템

## 1. 한눈에 보기

프로젝트는 기획 문서 정리, 프로토타입, 개발의 세 단계로 진행합니다. 단계 사이에는 관문이 있고, 관문의 완료 기준을 모두 채워야 다음 단계로 넘어갑니다. 일정은 아직 정하지 않아 날짜를 적지 않았습니다.

| 단계 | 목적 | 끝났다고 보는 기준 |
| --- | --- | --- |
| 1. 기획 문서 정리 | 무엇을 만들지 문서로 확정하고 형상관리를 시작합니다. | 필수 문서 네 개가 승인되고, 프로토타입 범위에 걸린 미정 사항이 없습니다. (관문 G1) |
| 2. 프로토타입 | 가장 불확실한 네 가지를 작게 만들어 확인합니다. | 파일럿 한 건이 프로젝트 정의서에서 화면설계서까지 완주하고, 진행 여부를 결정합니다. (관문 G2) |
| 3. 개발 | 요구사항 전체를 구현합니다. | 모든 요구사항이 수용 기준을 통과하고 실제 프로젝트 한 건에 적용합니다. |

지금은 1단계입니다.

## 3. 2단계: 프로토타입

전체를 만들기 전에 가장 불확실한 네 가지를 파일럿 한 건으로 확인합니다. 파일럿 대상은 이 시스템 자체(UX AI Studio 뷰어)입니다. 파일럿이 만드는 화면설계서가 뷰어의 설계가 되고, 그대로 [화면설계서](07-screen-spec.md) 문서를 채웁니다.

| 확인할 것 | 확인 방법 | 관련 요구사항 |
| --- | --- | --- |
| 구동 방식. Claude Code 웹과 GitHub 저장소에서 총괄 에이전트와 전문 에이전트 6개로 파이프라인이 끝까지 도는지, Max 한도 안에서 가능한지 | 파일럿 한 건을 완주하고 사용량을 기록 | REQ-003, REQ-006, REQ-019, REQ-020, REQ-024 |
| 문서 사슬의 품질. 요구사항에서 정책, 플로우, 화면까지 참조가 누락 없이 이어지는지 | 스크립트로 참조를 검사하고 사람이 고친 항목 수를 기록 | REQ-004, REQ-005, REQ-023 |
| 화면 렌더링. 화면설계서 JSON이 React 화면으로 그려지고 인터랙션이 동작하는지 | 파일럿 화면을 뷰어에서 실행 | REQ-007, REQ-012, REQ-013 |
| 검토와 승인. PR 검토와 병합이 기획자에게 쓸 만한 승인 방법인지 | 승인 지점 네 곳을 PR로 진행하고 사용자 의견을 기록 | REQ-009, REQ-010 |

만드는 것은 다음 다섯 가지입니다.

- **저장소 뼈대**: 총괄 규칙(CLAUDE.md), 전문 에이전트 명세 6개, JSON 스키마, 파일럿 프로젝트 폴더
- **프로젝트 정의서 템플릿**과 파일럿의 정의서
- **와이어프레임용 React 컴포넌트**: 파일럿 화면에 쓰는 블록만
- **최소 뷰어**: 문서 보기, 유저 플로우 다이어그램과 PNG 내보내기, 화면설계서 보기
- **검증 스크립트**: 스키마와 참조 검사

다음은 프로토타입에서 만들지 않고 개발 단계로 넘깁니다. 변경 추적과 부분 재생성, 검증 규칙 7개 전체, Figma와 PPTX 내보내기, 블록 등록 요청과 레지스트리 승인 절차, 예약 작업을 쓰는 자동화, 실제 Figma 추출, 진행 현황과 참조 관계 화면입니다.

프로토타입에서는 네 가지를 측정합니다.

- 전체 실행 한 번에 쓴 사용량과 한도에 닿아 멈춘 횟수
- 요구사항 반영률 (화면 영역에 연결된 요구사항 ÷ 전체 요구사항)
- 사람이 직접 고친 항목 수와 수정 요청 횟수
- 단계별로 걸린 시간

### 관문 G2의 완료 기준

- [ ] 파일럿 한 건이 프로젝트 정의서에서 화면설계서까지 완주했고, 승인 지점 네 곳을 사람이 승인했습니다.
- [ ] 파일럿 화면이 뷰어에서 동작합니다.
- [ ] 측정값 네 가지를 기록했습니다.
- [ ] 진행, 방향 수정, 중단 중 하나를 결정했습니다.
- [ ] 결과를 기획 문서에 반영하고 버전을 올렸습니다.

## 4. 3단계: 개발

프로젝트 정의서 9절의 개발 순서를 웹 구동 검토안에 맞춰 여덟 묶음으로 다시 나눴습니다. 묶음의 구성은 Claude의 제안이며 프로토타입 결과에 따라 바뀔 수 있습니다.

| 순서 | 작업 묶음 | 내용 | 관련 요구사항 |
| --- | --- | --- | --- |
| 1 | 데이터 규격과 검증 스크립트 | JSON 스키마, ID 규칙, 참조 검사, 프로젝트 정의서 템플릿 확정 | REQ-001, REQ-004, REQ-005, REQ-023 |
| 2 | 에이전트 명세와 총괄 규칙 | 전문 에이전트 명세 6개, 총괄 규칙, 권한 규칙과 훅, 승인 흐름, 실행 기록 | REQ-003, REQ-006, REQ-010, REQ-018 |
| 3 | 뷰어 (UX AI Studio) | 진행 현황, 문서 검토, 참조 관계, 플로우, 화면설계서 보기 | REQ-002, REQ-009, REQ-011, REQ-012, REQ-013 |
| 4 | UI 블록 라이브러리 연결 | 블록 레지스트리의 저장소화, 와이어프레임용 컴포넌트, 블록 검색, 신규 블록 등록 요청 | REQ-007, REQ-008 |
| 5 | 화면설계서 생성과 내보내기 | Screen Agent 보강, PPTX와 Figma 내보내기 | REQ-012, REQ-014 |
| 6 | 변경 추적과 검증 | 변경 감지, 영향 범위 분석, 부분 재생성, 검증 규칙 7개 | REQ-015, REQ-016, REQ-017 |
| 7 | 자동화 (선택) | 병합 후 영향 분석의 자동 실행, 뷰어의 실행 버튼. 리서치 프리뷰 기능에 의존합니다. | REQ-015 |
| 8 | 실제 프로젝트 적용 | 프로젝트 한 건에 적용하고 운영 가이드를 씁니다. | 전체 |

제약 요구사항(REQ-019~022)과 REQ-024는 모든 묶음에 적용합니다.

### 개발 단계의 완료 기준

- [ ] 요구사항 정의서의 모든 요구사항이 수용 기준을 통과했습니다.
- [ ] 실제 프로젝트 한 건에 적용했습니다.
- [ ] 기획 문서가 구현과 일치하고 버전을 올렸습니다.

## 5. 위험과 선결 사항

| 위험 | 영향 | 대응 |
| --- | --- | --- |
| Max 플랜의 사용량 한도 | 추가 크레딧을 쓰지 않으므로 한도에 닿으면 실행이 멈춥니다. | 프로토타입에서 사용량을 측정합니다. 단계별로 끊어 실행하고, 멈춘 실행을 저장소의 파일로 이어 갑니다. |
| ~~웹 구동 방식 미확정~~ | 해소됐습니다. | 2026-11-25에 확정하고 기능 정의서 0.4.0에서 3절·4절을 개정했습니다. |
| ~~파일럿 대상 미정~~ | 해소됐습니다. | 2026-11-25에 이 시스템 자체(뷰어)로 정했습니다. |
| 실제 UI 블록이 없음 | 블록 레지스트리는 목업이고 코드 연결도 가상이라 화면을 그릴 컴포넌트가 없습니다. | 프로토타입에서는 파일럿 화면, 곧 뷰어 화면 7개에 쓰는 블록만 컴포넌트로 만듭니다. |
| 리서치 프리뷰 기능 의존 | 예약 작업의 동작과 한도가 바뀔 수 있습니다. | 핵심 흐름은 일반 클라우드 세션만으로 돌아가게 하고 자동화는 선택으로 둡니다. |
| 고객사 제공 형태의 제한 | 구독 로그인을 다른 조직에 제공하는 형태는 Anthropic의 제한에 걸릴 수 있습니다. | 사내 도구 범위로 한정합니다. 넓힐 때는 Anthropic에 확인합니다. |
| 문서를 두 곳에서 관리 | Git 저장소와 Claude Docs의 내용이 어긋날 수 있습니다. | Git 저장소를 원본으로 하고 변경은 Git에서 먼저 합니다. |
