# 파이프라인 v2: 설계서를 코드로 옮기는 네 단계

## 1. 문서 개요

[에이전트 명세](09-agent-spec.md)가 정한 01~06을 **그대로 두고**, 그 뒤에 07~10을 더합니다. 설계서가 승인된 뒤 코드를 만들고 검증하는 구간입니다.

| 항목 | 내용 |
| --- | --- |
| 상태 | 검토 필요. **전부 제안입니다.** 사람의 확정 전입니다. |
| 고치지 않는 것 | 01~06의 단계·에이전트·게이트·자물쇠. [AGT](09-agent-spec.md)가 기준입니다 |
| 더하는 것 | 07 UI Implementation, 08 Wireframe Rendering, 09 Implementation QA, 10 Prototype Review |
| 전제 | [MVP 간극 분석](MVP_GAP_ANALYSIS.md) 4절, [UI 블록 커버리지](UI_BLOCK_COVERAGE.md) |

### 왜 더하는가

[간극 분석](MVP_GAP_ANALYSIS.md) 4절이 센 것입니다. 층이 둘인데 하나만 자동화돼 있습니다.

| 층 | 지금 |
| --- | --- |
| 사람이 보는 계획 — [DRM](11-dev-roadmap.md)의 M0~M7 | 있습니다 |
| 에이전트가 도는 단계 — `STAGES`, `.claude/agents/` | **01~06뿐입니다** |

설계서를 코드로 옮기는 일에 **시작 조건도 완료 조건도 담당 에이전트도 없습니다.** 01~06이 쌓아 온 것들 — 게이트가 판정하고, 자물쇠가 동시 실행을 막고, 실패하면 담당 에이전트를 다시 부르고, `runs.json`에 남기는 것 — 이 구간에서는 아무것도 작동하지 않습니다.

## 2. 먼저 풀어야 할 것 — 자물쇠가 코드에는 안 걸립니다

**이 제안의 가장 큰 미정 사항입니다.** 넘어가지 말고 먼저 적습니다.

01~06의 자물쇠는 **문서 단위**로 걸립니다. `_meta/status.json`의 문서 코드가 `생성 중`이면 `runs.json`의 끝나지 않은 실행이 그 문서를 쥐고, 쓰기 전 훅이 다른 세션의 쓰기를 막습니다. 훅은 경로를 보고 어느 문서인지 가립니다.

```python
if rest.startswith("screens/") or rest == "STORYBOARD.md":
    return pid, "SB"
```

**코드는 문서가 아닙니다.** `viewer/src/blocks/GlobalHeader.tsx`는 어느 문서 코드에도 속하지 않습니다. 길이 셋입니다.

| 길 | 방법 | 값 |
| --- | --- | --- |
| **가** | `viewer/`를 프로젝트 산출물로 보고 문서 코드 `UI`를 줍니다. 훅의 `target_doc`에 경로 한 줄을 더합니다 | 기존 기계가 그대로 돕니다. 다만 뷰어가 프로젝트 하나에 묶입니다 |
| **나** | 블록 단위로 자물쇠를 겁니다. `blocks.json`에 블록마다 상태를 둡니다 | 블록 여럿을 병렬로 만들 수 있습니다. 기계를 새로 만들어야 합니다 |
| **다** | 코드에는 자물쇠를 걸지 않습니다. 브랜치와 PR로만 막습니다 | 만들 것이 없습니다. 같은 파일을 두 세션이 동시에 고치면 덮입니다 |

**가**를 제안합니다. 2026-11-26에 자물쇠 없이 두 세션이 같은 단계를 돌려 산출물이 서로 덮인 일이 있었고, 그때 자물쇠를 만든 까닭이 그대로 코드에도 적용되기 때문입니다. 다만 뷰어가 프로젝트 폴더 바깥(`viewer/`)에 있다면 경로 대응을 어떻게 할지 함께 정해야 합니다.

**이것이 정해지기 전에는 07~10을 돌리지 않습니다.**

## 3. 단계 한눈에

| 단계 | 에이전트 | 만드는 것 | 시작 조건 |
| --- | --- | --- | --- |
| 07 UI Implementation | `implement` | 블록 컴포넌트와 `blocks.json` | 화면설계서 승인 + 블록 하나를 고름 |
| 08 Wireframe Rendering | `render` | 렌더러·화면·라우팅과 `render.json` | P0 블록이 모두 `구현됨` |
| 09 Implementation QA | `impl-qa` | `IMPL-QA-REPORT.md`, `impl-validation.json` | 08 생성 완료 |
| 10 Prototype Review | 사람 + `review` | `PROTOTYPE-REVIEW.md` | 09의 규칙을 모두 통과 |

01~06과 같은 규칙을 그대로 따릅니다. 총괄은 **문서도 코드도 직접 쓰지 않고** 게이트 검사·상태 갱신·사람에게 묻기만 합니다. 완료 조건을 못 채우면 검토로 넘기지 않고 **같은 에이전트를 다시 부릅니다**(POL-008). 상태를 `승인`으로 바꾸지 않습니다(POL-002).

## 4. 07 UI Implementation

### 역할

`STORYBOARD.md`와 화면 파일, 그리고 레지스트리의 블록 명세를 읽어 **블록 하나를 React 컴포넌트로 만듭니다.** 화면설계서를 고치지 않습니다.

### 입력

| 자료 | 쓰임 |
| --- | --- |
| `screens/SCR-*.json` | 그 블록을 쓰는 영역의 `props`·`interactions`·`exceptions` |
| `STORYBOARD.md` 9절 | 블록을 고른 근거, 등록 요청의 까닭 |
| `reference/uxui-registry-mock/blocks/**` | `BLK-*`의 `spec.props`·`variants`·`tokens`·`layout` |
| [UI 블록 커버리지](UI_BLOCK_COVERAGE.md) | 분류와 우선순위, 구현 공유 제안 |
| `viewer/src/tokens/` | CSS 변수 토큰 |

### 시작 조건

```
python3 scripts/check_gate.py <project-id> --stage implement --phase start --block BLK-0001
```

| 조건 | 까닭 |
| --- | --- |
| `SB`가 `승인` | 승인되지 않은 설계로 코드를 만들지 않습니다 |
| 사용자가 블록을 고름 | 화면설계서가 작업 단위를 고르게 한 것과 같습니다 |
| 그 블록을 쓰는 영역이 하나 이상 | 쓰이지 않는 블록을 만들지 않습니다 |
| 2절의 자물쇠 방식이 정해짐 | **지금은 이것 때문에 시작할 수 없습니다** |

### 작업 내용

1. 그 블록을 쓰는 **모든 영역의 `props` 키를 모읍니다.** 키 하나라도 빠지면 그 영역이 그려지지 않습니다.
2. `BLK-*`이면 레지스트리의 `spec.props`와 영역의 `props`가 **같은 이름인지** 대조합니다. 다르면 고치지 말고 보고합니다(POL-026).
3. 컴포넌트를 만듭니다. 파일 하나가 블록 하나이고, **블록 ID와 버전과 props 이름을 파일에 적습니다**(DEV 8절). 나중에 레지스트리의 코드 연결 정보로 그대로 올립니다.
4. 영역의 `exceptions`에 적힌 상황을 **컴포넌트가 실제로 보일 수 있게** 만듭니다. '읽지 못했습니다', '비어 있습니다' 같은 것들입니다.
5. 색·여백·타이포는 `spec.tokens`의 이름을 CSS 변수로 받습니다. 값을 직접 적지 않습니다.
6. `blocks.json`에 그 블록 줄을 더합니다.

### 출력

| 파일 | 내용 |
| --- | --- |
| `viewer/src/blocks/<Name>/<Name>.tsx` | 컴포넌트 |
| `viewer/src/blocks/<Name>/<Name>.module.css` | 토큰을 쓰는 스타일 |
| `viewer/src/blocks/<Name>/<Name>.test.tsx` | 단위 시험 |
| `blocks.json` | 블록마다 `{ block_id, version, component, path, props, areas, state, origin, updated_at }` |

`blocks.json`의 `state`는 문서 상태 다섯과 같은 값을 씁니다(POL-005). `대기 → 수정 필요 → 생성 중 → 검토 필요 → 승인` 차례도 그대로입니다.

### 완료 조건

```
python3 scripts/check_gate.py <project-id> --stage implement --phase complete --block BLK-0001
```

| 검사 | 내용 |
| --- | --- |
| props 덮기 | 그 블록을 쓰는 모든 영역의 `props` 키가 컴포넌트의 prop에 있다 |
| 이름 일치 | props 키가 코드의 prop 이름과 **글자 그대로** 같다 (POL-026) |
| 예외 구현 | 영역의 `exceptions`마다 그것을 보이는 길이 코드에 있다 |
| 토큰 | 색·여백·타이포에 하드코딩한 값이 없다 |
| 시험 | 단위 시험이 통과한다 |
| 쓰기 없음 | 네트워크 쓰기 호출이 없다 (POL-034) |
| `blocks.json` | 줄이 있고 `block_id`·`version`·`props`가 화면 파일과 맞는다 |

### 실패 시

`implement`를 다시 부르고 게이트 출력을 그대로 전달합니다. `runs.json`의 `attempt`를 올립니다. **props 이름이 레지스트리와 다르면 고치지 말고 사람에게 묻습니다** — 화면설계서를 고칠지 레지스트리에 등록 요청을 낼지는 사람이 정합니다.

## 5. 08 Wireframe Rendering

### 역할

블록을 화면으로 **엮습니다.** 화면 파일을 읽어 영역을 순서대로 그리고, 이동을 라우팅으로 잇고, 인터랙션을 React State로 돌립니다. **블록을 만들지 않습니다.**

### 입력

| 자료 | 쓰임 |
| --- | --- |
| `screens/SCR-*.json` | `areas` 순서, `state` 초기값, `interactions`의 `set` |
| `ia.json` | `transitions` 21건 → 라우팅 |
| `blocks.json` | 블록 ID → 컴포넌트 대응표 |
| [DEV](10-dev-architecture.md) 5절 | 렌더러 구조, `data/load.ts` 경계 |

### 시작 조건

```
python3 scripts/check_gate.py <project-id> --stage render --phase start
```

| 조건 | 까닭 |
| --- | --- |
| P0 블록 9종이 모두 `blocks.json`에서 `검토 필요` 이상 | 렌더러가 그릴 것이 있어야 합니다 |
| `IA`가 `승인` | 이동이 정해져 있어야 라우팅을 겁니다 |

**P0만으로 시작합니다.** 48개 영역 가운데 26개가 덮이고(COV 5절), 나머지는 `BRQ-0011`이 '블록을 그리지 못했습니다'로 그립니다. **그 자리가 남은 일의 목록이 됩니다.**

### 작업 내용

1. `data/load.ts`를 만듭니다. 화면이 파일 경로를 직접 알지 않습니다(DEV 9절).
2. 화면 일곱 장을 만듭니다. 영역을 **화면 파일에 적힌 순서 그대로** 그립니다.
3. `ia.json`의 `transitions`를 라우팅으로 겁니다. `trigger`가 같은 두 줄은 두 길입니다.
4. 인터랙션을 React State로 돌립니다. `set`이 가리키는 키가 그 화면의 `state`에 있어야 합니다.
5. 못 찾은 블록은 **건너뛰지 않고** 블록 ID와 안내를 보입니다(`SCR-005-A03`의 예외).
6. `render.json`에 화면마다 무엇이 그려졌고 무엇이 비었는지 적습니다.

### 출력

| 파일 | 내용 |
| --- | --- |
| `viewer/src/screens/<SCR-000>/` | 화면 |
| `viewer/src/data/load.ts` | 저장소 읽기의 유일한 통로 |
| `viewer/src/render/` | 영역 렌더러, 블록 대응표 |
| `render.json` | 화면마다 `{ screen_id, areas_rendered, areas_unrendered, transitions_wired }` |

### 완료 조건

| 검사 | 내용 |
| --- | --- |
| 영역 순서 | 그려진 순서가 화면 파일의 `areas` 순서와 같다 |
| 영역 수 | 화면마다 그린 자리(안내 포함)의 수가 `areas` 수와 같다 |
| 이동 | `transitions` 21건이 모두 걸려 있다 |
| 인터랙션 | 모든 `set`이 그 화면 `state`의 키다 |
| 읽기 전용 | 쓰기 호출이 없다 (POL-034) |
| 승인 버튼 없음 | 승인하는 자리가 없다 (POL-002) |
| 빌드 | 빌드가 통과한다 |

### 실패 시

`render`를 다시 부릅니다. **블록이 없어서 생긴 미구현 자리는 실패가 아닙니다.** `render.json`에 적히고 07로 돌아가 그 블록을 만듭니다.

## 6. 09 Implementation QA

### 역할

**코드와 설계서가 같은 말을 하는지 판정합니다.** 판정만 하고 고치지 않습니다. 06 QA가 문서끼리 대조하는 것과 같은 자리입니다.

### 검증 규칙 (제안)

| 규칙 | 확인 내용 | 실패 시 담당 |
| --- | --- | --- |
| IQ-01 영역 덮기 | 영역 48개 가운데 몇 개가 실제로 그려지는가. 비율을 `metric`에 적는다 | `implement` |
| IQ-02 props 이름 | 화면 파일의 `props` 키와 컴포넌트의 prop 이름이 글자 그대로 같은가 (POL-026) | `implement` |
| IQ-03 영역 순서 | 그려진 순서가 화면 파일과 같은가 (POL-014) | `render` |
| IQ-04 인터랙션 | `interactions`의 `set`이 모두 돌아가는가 | `render` |
| IQ-05 예외 재현 | 영역의 `exceptions`마다 그 상황을 화면에서 만들 수 있는가 | `implement` |
| IQ-06 이동 | `transitions`가 모두 걸려 있고 끊긴 길이 없는가 | `render` |
| IQ-07 경계 | 쓰기 호출·승인 버튼·실행 버튼이 없는가 (DEV 9절) | `render` |
| IQ-08 블록 유효성 | `blocks.json`의 블록이 레지스트리 또는 등록 요청과 맞는가 | `implement` |

**IQ-07이 가장 중요합니다.** 설계가 지키라고 한 경계를 코드가 깨뜨리는 자리이고, 문서 검사로는 잡히지 않습니다.

### 출력

| 파일 | 내용 |
| --- | --- |
| `IMPL-QA-REPORT.md` | 사람이 읽는 판정 |
| `impl-validation.json` | 규칙마다 `{ rule, result, targets, owner_agent, metric }` |

`validation.json`과 같은 스키마를 씁니다(DATA 4절).

### 실패 시

`impl-validation.json`의 `owner_agent`가 가리키는 에이전트를 부릅니다. **총괄이 임의로 고르지 않습니다.** 06 QA와 같습니다.

## 7. 10 Prototype Review

### 역할

**사람이 뷰어를 직접 써 보고 판정합니다.** 에이전트는 볼 거리를 차려 주기만 합니다.

### 시작 조건

09의 규칙 여덟을 모두 통과해야 합니다. **하나라도 실패면 사람을 부르지 않습니다.**

### 작업 내용

`review` 에이전트가 **걸어 볼 길**을 만듭니다. 설계서에 적힌 것 가운데 사람이 눈으로 확인해야 하는 것들입니다.

| 차리는 것 | 어디서 왔는가 |
| --- | --- |
| 화면 일곱 장을 도는 길 | `ia.json`의 `transitions` 21건 |
| 예외 상황 재현 목록 | 영역의 `exceptions` |
| 그리지 못한 영역 목록 | `render.json`의 `areas_unrendered` |
| 설계와 다르게 보이는 곳 | `impl-validation.json`에서 통과했지만 눈으로 봐야 하는 것 |

### 출력

`PROTOTYPE-REVIEW.md`에 사람이 본 것과 판단을 적습니다. **에이전트가 이 문서의 판정 칸을 채우지 않습니다.**

### 끝난 뒤

| 결과 | 다음 |
| --- | --- |
| 통과 | 사람이 PR을 병합해 승인합니다 (POL-002) |
| 고칠 것이 있음 | 설계가 틀렸으면 05로, 코드가 틀렸으면 07·08로 돌아갑니다 |

**설계로 돌아가는 길이 있는 것이 중요합니다.** 그려 보고 나서야 드러나는 것이 있고, 그때 화면설계서를 고치면 `SB`가 다시 `검토 필요`로 내려가 06부터 다시 돕니다.

## 8. 01~06과 달라지는 것

| 항목 | 01~06 | 07~10 |
| --- | --- | --- |
| 만드는 것 | 문서 (Markdown + JSON 짝) | 코드 (`.tsx`, `.css`) + 상태 JSON |
| 자물쇠 | 문서 코드마다 | **미정.** 2절 |
| 되풀이 단위 | 작업 단위 (WU) | 블록 (07), 화면 전체 (08) |
| 완료 조건 | 참조 무결성, 스키마 | **빌드와 시험이 통과하는가** |
| 병렬 | 금지 (같은 파일을 씀) | 블록은 파일이 갈려 **가능할 수 있음**. 2절에 걸림 |

**완료 조건에 빌드와 시험이 들어오는 것이 가장 큰 차이입니다.** 01~06의 게이트는 JSON을 읽어 판정했지만, 07~10은 `npm run build`와 `vitest`를 돌려야 합니다. `check_gate.py`가 외부 명령을 부르게 되므로 **시간이 오래 걸리고 환경에 기댑니다.**

## 9. 미정 사항

| 사항 | 정해야 하는 것 |
| --- | --- |
| **자물쇠를 코드에 어떻게 걸 것인가** | 2절의 가·나·다. **이것이 정해지기 전에는 07~10을 돌리지 않습니다** |
| 뷰어 코드의 자리 | `viewer/`인지 별도 저장소인지. 자물쇠 방식이 여기에 걸립니다 |
| 게이트가 빌드를 부를 것인가 | 부르면 느리고 환경에 기댑니다. 안 부르면 완료 조건이 헐거워집니다 |
| 블록을 병렬로 만들 것인가 | 파일이 갈리므로 가능해 보이나 `blocks.json`을 함께 씁니다 |
| 새 문서 코드 네 개 | `UI`, `RND`, `IQA`, `PRV`를 [데이터 규격](08-data-spec.md) 3절의 ID 규칙에 넣을지 |
| 09의 규칙 번호 | `IQ-01`로 제안했습니다. 기존 `QA-01`과 섞이지 않게 접두어를 가를지 |
| 10을 에이전트 단계로 둘 것인가 | 사람이 하는 일인데 파이프라인 단계로 세면 `runs.json`에 남는 것이 애매합니다 |
