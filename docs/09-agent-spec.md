# 에이전트 명세: AI UX 설계 자동화 시스템

## 1. 문서 개요

이 문서는 총괄 에이전트 1개와 전문 에이전트 6개의 명세입니다. 에이전트마다 읽는 것, 만드는 것, 시작 조건, 완료 조건, 하지 말아야 할 것을 적습니다.

웹 구동 방식 확정(2026-11-25)에 따라 이 문서는 저장소의 다음 파일로 옮겨집니다.

| 이 문서의 절 | 저장소의 파일 |
| --- | --- |
| 2절 총괄 규칙 | `CLAUDE.md` |
| 3~8절 전문 에이전트 6개 | `.claude/agents/requirements.md` 등 6개 |
| 9절 권한 규칙과 훅 | `.claude/settings.json` |

| 항목 | 내용 |
| --- | --- |
| 상태 | 검토 필요. Claude가 쓴 초안이며 사람의 승인 전입니다. |
| 기준 문서 | [기능 정의서](03-functional-spec.md) 7절, [정책서](02-policy.md) 3절, [데이터 규격](08-data-spec.md) |
| 확정 전 입력 | 에이전트 실행 정책 POL-007~012는 아직 제안입니다. 이 문서는 그 정책이 그대로 확정된다고 보고 썼습니다. |

## 2. 총괄 규칙

주 세션이 총괄 에이전트 역할을 합니다. 문서를 직접 쓰지 않고, 작업을 나눠 주고 문서 간 연결을 관리합니다.

### 실행 순서

```
PROJECT.md (사람)
  └─ 01 Requirements ─ 02 Policy ─┬─ 03-A Flow (UF) ─┐
                                  └─ 03-B Flow (WF) ─┴─ 04 IA ─ 05 Screen ─ 06 QA
```

유저 플로우와 워크 플로우는 한쪽을 끝내고 다른 쪽을 쓰지 않고 서로 참조하며 함께 정의합니다(POL-012).

### 한 단계의 처리

1. `_meta/status.json`에서 시작 조건을 확인합니다. 조건이 안 되면 실행을 보류하고 사람에게 무엇이 막혔는지 알립니다.
2. 해당 문서의 상태를 `생성 중`으로 바꿉니다.
3. 전문 에이전트(서브에이전트)에 생성을 맡깁니다.
4. 검증 스크립트로 스키마와 완료 조건을 검사합니다.
5. 완료 조건을 못 채우면 검토로 넘기지 않고 같은 에이전트를 다시 실행합니다(POL-008). 실행할 때마다 `runs.json`의 `attempt`를 올립니다.
6. 통과하면 상태를 `검토 필요`로 바꾸고, 작업 브랜치에 푸시해 PR을 엽니다.
7. `runs.json`에 실행 기록을 남깁니다(POL-033).

### 시작 조건

| 단계 | 시작 조건 |
| --- | --- |
| 01 Requirements | `project.json`의 `confirmed`가 `true` |
| 02 Policy | 요구사항 정의서 생성 완료 |
| 03-A·03-B Flow | 정책서 생성 완료 |
| 04 IA | 유저 플로우와 워크 플로우 생성 완료 |
| 05 Screen | 정보 구조도 승인, 사용자가 작업 단위를 선택함 |
| 06 QA | 화면설계서 생성 완료 |

초안은 승인 전에도 만들 수 있습니다. 선행 문서가 승인 전이어도 생성이 끝났으면 다음 에이전트를 실행합니다(POL-007). 다만 01 Requirements는 사람이 정의서를 확정한 뒤에, 05 Screen은 정보 구조도가 승인되고 사용자가 작업 단위를 고른 뒤에 시작합니다(POL-037).

화면설계서 단계는 작업 단위별로 되풀이합니다. 총괄 에이전트가 승인된 작업 단위 목록과 상태를 보여 주고, 사용자가 고른 작업 단위에 대해 위의 한 단계 처리(상태 변경, 생성, 검사, PR)를 합니다. 처리 순서는 [워크 플로우](05-workflow.md) WF-001~010에 있습니다.

### 상황별 처리

프로젝트 정의서 6절의 표를 따릅니다.

| 상황 | 처리 |
| --- | --- |
| 선행 문서 미완성 | 다음 에이전트 실행 보류 |
| 필수 정보 부족 | 이전 에이전트에 보완 요청 |
| 정책과 플로우 충돌 | Policy Agent와 Flow Agent 재실행 |
| 화면 누락 발견 | IA Agent에 수정 요청 |
| UI 블록 미존재 | 라이브러리 검색 또는 신규 블록 등록 요청 |
| 최종 검증 실패 | 담당 에이전트에 수정 요청 |
| 최종 검증 통과 | 사람이 화면설계서 PR을 병합하면 프로젝트를 승인 상태로 바꿈 |

### 총괄 에이전트가 하지 않는 것

- 문서를 직접 쓰지 않습니다. 고칠 것이 있으면 담당 에이전트를 다시 실행합니다.
- 문서 상태를 `승인`으로 바꾸지 않습니다. 승인은 사람이 PR을 병합할 때만 일어납니다(POL-002).
- 사용량 한도에 닿아 멈추면 이어서 하려고 다시 시도하지 않습니다. `runs.json`에 `중단`으로 남기고 멈춥니다. 사람이 다시 지시하면 저장소의 파일을 읽어 이어 갑니다(POL-029).

## 3. Requirements Agent

| 항목 | 내용 |
| --- | --- |
| 읽는 것 | `PROJECT.md`, `project.json` |
| 만드는 것 | `PRD.md`, `requirements.json` |
| 시작 조건 | `project.json`의 `confirmed`가 `true` |
| 완료 조건 | 모든 요구사항에 `id`, `priority`, `acceptance`가 있다. `project.json`의 목표(`GOAL-00`)마다 요구사항이 하나 이상 연결된다. |

- 요구사항을 지어내지 않고 정의서에서 뽑습니다. 정의서에 없는 것이 필요하면 만들지 말고 총괄 에이전트에 보완을 요청합니다.
- 유형은 기능, 비기능, 제약 중 하나입니다.
- 수용 기준은 확인할 수 있게 씁니다. "빠르다"가 아니라 "3초 안에 응답한다"입니다.

## 4. Policy Agent

| 항목 | 내용 |
| --- | --- |
| 읽는 것 | `requirements.json` |
| 만드는 것 | `POLICY.md`, `policies.json` |
| 시작 조건 | 요구사항 정의서 생성 완료 |
| 완료 조건 | 모든 정책이 `REQ`를 하나 이상 참조한다. `conditions`, `states`, `exceptions`가 적혀 있다. |

- 어느 요구사항에도 걸리지 않는 정책은 만들지 않습니다. QA-02가 참조되지 않는 정책을 찾아냅니다.
- `exceptions`에 적은 예외는 나중에 Screen Agent가 화면 영역에 옮겨 적어야 합니다(QA-05). 화면에서 다룰 수 없는 예외는 적지 않습니다.
- 상태값을 정의할 때 ERD가 없다는 것을 전제합니다. 상태와 조건은 정책서가, 데이터 흐름은 워크 플로우가 맡습니다(POL-032).

## 5. Flow Agent

유저 플로우와 워크 플로우를 함께 만듭니다. 한 에이전트가 둘을 맡는지는 미정입니다(10절).

| 항목 | 내용 |
| --- | --- |
| 읽는 것 | `requirements.json`, `policies.json` |
| 만드는 것 | `USER-FLOW.md`, `user-flow.json`, `WORKFLOW.md`, `workflow.json` |
| 시작 조건 | 정책서 생성 완료 |
| 완료 조건 | 모든 분기(`step_type`이 `분기`)에 `policy`가 있다. 유저 플로우의 단계마다 대응하는 워크 플로우 처리(`user_step`)가 있다. |

- 분기 조건을 스스로 정하지 않습니다. 정책에 없는 분기가 필요하면 총괄 에이전트에 알려 Policy Agent를 다시 실행하게 합니다.
- `screen` 필드는 비워 둡니다. IA Agent가 채웁니다.
- 이탈(`이탈`) 단계를 빠뜨리지 않습니다. 완료만 있는 플로우는 완료 조건을 못 채운 것으로 봅니다.

## 6. IA Agent

| 항목 | 내용 |
| --- | --- |
| 읽는 것 | `user-flow.json`, `workflow.json`, `requirements.json` |
| 만드는 것 | `IA.md`, `ia.json` |
| 시작 조건 | 유저·워크 플로우 생성 완료 |
| 완료 조건 | 플로우의 모든 화면 단계가 `SCR`에 배정됐다. `transitions`의 대상 화면이 모두 존재한다. 모든 `SCR`이 작업 단위 하나에 속한다. |

- 화면을 배정하면서 `user-flow.json`의 `screen` 필드를 채웁니다. 이것이 자기 문서 밖 쓰기의 유일한 예외이며, 훅 설정에 예외로 적습니다(9절).
- 화면 간 이동은 플로우의 `next`와 어긋나지 않아야 합니다(QA-03).
- 메뉴 계층을 지어내지 않습니다. 플로우에 나오지 않는 화면은 만들지 않습니다.
- 화면을 작업 단위(`WU-000`)로 묶어 `ia.json`의 `work_units`에 제안합니다(POL-035). 작업 단위는 사람이 정보 구조도를 승인해야 화면설계서 작성의 선택지가 됩니다.

## 7. Screen Agent

| 항목 | 내용 |
| --- | --- |
| 읽는 것 | 모든 선행 문서, UI 블록 라이브러리(커넥터) |
| 만드는 것 | `STORYBOARD.md`, `screens/SCR-000.json` |
| 시작 조건 | 정보 구조도 승인, 작업 단위 선택 |
| 완료 조건 | 선택된 작업 단위의 모든 `SCR`에 화면 파일이 있다. 영역마다 블록, 요구사항, 정책이 연결되고 `exceptions`가 적혀 있다. |

- 선택된 작업 단위의 화면만 만듭니다. 다른 작업 단위의 화면 파일은 고치지 않습니다(POL-037).
- 블록은 Core 가이드, 표준 블록 순으로 찾고, 블록의 "쓰는 상황"과 "쓰지 않을 때"를 근거로 고릅니다(POL-022). 사람이 확인하지 않은 AI 초안 가이드는 근거에서 뺍니다.
- 블록은 ID와 Major 버전 범위로 참조합니다(POL-023). 폐기된 블록은 쓰지 않습니다.
- 맞는 블록이 없으면 프로젝트 블록으로 만들고 등록 요청 `BRQ-0000`을 남깁니다. 표준 블록 폴더에 직접 쓰지 않습니다(POL-024).
- `props`의 키는 React 컴포넌트의 prop 이름을 그대로 씁니다(POL-026). 한글 슬롯 이름을 쓰지 않습니다.
- `interactions`의 `set`은 그 화면 `state`의 키여야 합니다. 없는 state를 가리키지 않습니다.
- 연결한 정책의 `exceptions`를 영역의 `exceptions`에 빠짐없이 옮깁니다(QA-05).

## 8. QA Agent

| 항목 | 내용 |
| --- | --- |
| 읽는 것 | 프로젝트 폴더 전체 |
| 만드는 것 | `QA-REPORT.md`, `validation.json` |
| 시작 조건 | 화면설계서 생성 완료 |
| 완료 조건 | 기능 정의서 9절의 규칙 7개를 모두 판정했다. |

| 규칙 | 확인 내용 | 실패 시 담당 |
| --- | --- | --- |
| QA-01 요구사항 반영 | 모든 `REQ`가 화면 영역 하나 이상에 연결됐다. 반영률을 `metric`에 기록한다. | IA Agent, Screen Agent |
| QA-02 정책 일치 | 플로우와 화면이 참조한 `POL`과 어긋나지 않는다. 참조되지 않는 `POL`이 없다. | Policy Agent, Flow Agent, Screen Agent |
| QA-03 플로우 연결 | 모든 유저 플로우 단계가 화면에 배정되고 분기가 정책에 연결됐다. 유저 플로우와 워크 플로우가 대응한다. | Flow Agent |
| QA-04 화면 누락 | 모든 `SCR`에 화면 파일이 있고 이동 대상 화면이 존재한다. | IA Agent, Screen Agent |
| QA-05 예외 처리 | 정책의 예외마다 해당 화면 영역에 예외 상황이 적혀 있다. | Screen Agent |
| QA-06 승인 상태 | 승인된 문서가 미승인 항목을 참조하지 않는다. | 총괄 에이전트 |
| QA-07 블록 유효성 | 쓴 블록이 라이브러리에 있고 폐기 상태가 아니다. 등록 요청 중인 블록은 따로 표시한다. | Screen Agent |

- QA Agent는 판정만 하고 다른 문서를 고치지 않습니다. 실패 항목은 `owner_agent`에 담당을 적어 총괄 에이전트에 넘깁니다.
- 7개를 모두 통과해야 화면설계서의 최종 승인이 열립니다(POL-021).

## 9. 권한 규칙과 훅

저장소의 `.claude/settings.json`으로 막습니다. 규칙을 벗어난 결과가 병합되지 않도록 PR 단계의 검사와 함께 둡니다.

| 막는 것 | 방법 |
| --- | --- |
| 자기 문서 밖 쓰기 | 에이전트마다 쓰기 가능한 경로를 지정합니다. 예외는 IA Agent가 `user-flow.json`의 `screen` 필드를 채우는 것 하나입니다(6절). |
| 사람이 고친 항목 덮어쓰기 | 쓰기 전 훅이 대상 항목의 `origin`을 확인하고, `human`이면 막고 사람에게 묻습니다(POL-010). |
| 상태를 승인으로 바꾸기 | 쓰기 전 훅이 `status.json`에 **새로** `승인`이 생기는지 보고 막습니다(POL-002). 이미 `승인`인 것을 그대로 둔 쓰기는 막지 않습니다. |
| 표준 블록 폴더에 직접 쓰기 | 블록 레지스트리의 표준 블록 경로를 읽기 전용으로 둡니다(POL-024). |
| ID 변경과 재사용 | 검증 스크립트가 이전 커밋과 ID 집합을 비교합니다. 사라진 ID가 있으면 실패입니다. |
| 남의 실행이 쥔 문서에 쓰기 | 쓰기 전 훅이 문서 상태가 `생성 중`인지 보고, 맞으면 `runs.json`의 끝나지 않은 실행과 `session`을 견줘 주인이 아니면 막습니다. |

훅은 막는 데만 씁니다. 훅이 문서를 고치지 않습니다. 고칠 것이 있으면 담당 에이전트를 다시 실행합니다.

### 자물쇠

`생성 중`은 처음부터 "지금 누가 만들고 있다"는 뜻이었지만 2026-11-26까지 읽는 코드가 없었습니다. 같은 날 두 세션이 같은 단계를 동시에 돌려 유저 플로우 산출물이 서로 덮이고 나서 자물쇠로 구현했습니다.

주인은 `_meta/runs.json`에서 `finished_at`이 빈 실행이 쥡니다. 주인을 가리는 열쇠는 훅이 받는 세션 식별자입니다. 서브에이전트의 쓰기에도 주 세션과 같은 값이 오므로, 총괄이 부른 에이전트는 통과하고 다른 세션만 막힙니다.

| 상황 | 결과 |
| --- | --- |
| 문서 상태가 `생성 중`이 아님 | 통과. 쥔 사람이 없습니다 |
| `생성 중` + 내 세션이 쥔 실행이 있음 | 통과 |
| `생성 중` + 다른 세션이 쥐고 있음 | 막음 |
| `생성 중` + 끝나지 않은 실행이 없음 | 막음. 끊긴 실행이므로 사람이 봐야 합니다 |
| `_meta/`와 프로젝트 정의서 | 자물쇠를 걸지 않습니다. 총괄과 사람의 것입니다 |

자물쇠는 Markdown과 JSON에 모두 걸립니다. 화면설계서는 `screens/` 아래 전부와 `STORYBOARD.md`가 대상입니다. **`STORYBOARD.md`는 프로젝트에 하나뿐이라 작업 단위를 병렬로 돌리면 충돌합니다.** 작업 단위는 하나씩 돌립니다.

세션 식별자를 알 수 없거나 스크립트를 읽지 못하면 막지 않습니다. 자물쇠가 저장소를 잠가 버리는 것보다 낫다고 보았습니다. (제안)

회귀 시험은 `scripts/test_guard.py`입니다.

### 승인을 막는 검사가 쓰기 전후를 견줘야 하는 까닭

처음에는 쓰기 **결과**에 `승인`이 있으면 막았습니다. 그러면 사람이 한 번 승인한 뒤로 총괄이 `status.json`에 아무것도 쓸 수 없습니다. 다음 단계를 `생성 중`으로 바꾸는 것까지 막혀 파이프라인이 그 자리에서 섭니다. 2026-11-26에 정보 구조도를 승인한 직후 실제로 그렇게 섰습니다.

지금은 쓰기 전 파일과 견줘 **없던 `승인`이 새로 생길 때만** 막습니다. 문서 상태와 작업 단위 상태를 함께 봅니다.

승인을 기록하는 주체는 아직 정해지지 않았습니다. `POL-002`는 사람이 PR을 병합할 때 승인이 일어난다고 정했지만, 병합된 사실을 `status.json`에 적는 자리가 비어 있습니다. 지금은 사람이 직접 고칩니다. 미정 사항에 올렸습니다.

## 10. 미정 사항

- [ ] Flow Agent 하나가 유저 플로우와 워크 플로우를 함께 만드는지, 둘로 나눌지 (POL-012)
- [ ] 같은 문서를 다시 실행할 수 있는 횟수의 한도 (POL-008)
- [ ] 쓸 모델. Max 한도 안에서 하루에 돌릴 수 있는 실행량은 파일럿에서 측정합니다(POL-029).
- [ ] 에이전트 실행 정책 POL-007~012의 확정. 지금은 제안이며 이 문서가 그 위에 서 있습니다.
- [ ] 블록 레지스트리의 `AGENTS.md`를 이 시스템의 `CLAUDE.md`에 어떻게 연결할지
- [ ] IA Agent의 `screen` 필드 쓰기 예외를 그대로 둘지, 별도 단계로 뺄지 (제안)
- [ ] 작업 단위 검증에서 QA Agent가 판정할 규칙의 범위 (POL-039, 제안)
- [ ] 끊긴 실행을 누가 닫는지. 지금은 자물쇠가 막고 사람을 부릅니다. 총괄이 스스로 닫게 할지 정해야 합니다.
- [ ] 병합된 사실을 `status.json`에 적는 주체. `POL-002`는 사람이 PR을 병합할 때 승인된다고 정했지만 그것을 기록하는 자리가 없습니다. 지금은 사람이 직접 고칩니다. GitHub Actions로 둘지 정해야 합니다.
- [ ] 총괄이 문서를 직접 쓰지 않는다는 규칙(2절)에는 아직 막는 장치가 없습니다. 훅이 받는 `agent_type`으로 볼 수 있습니다. (제안)
