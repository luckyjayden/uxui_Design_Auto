# 개발 로드맵: AI UX 설계 자동화 시스템

## 1. 문서 개요

이 문서는 [개발 아키텍처](10-dev-architecture.md)가 정한 구조를 **어떤 순서로 만들지**를 정합니다. 구현 단위를 MVP 일곱 개로 나누고, 각각의 완료 기준을 확인할 수 있게 적습니다.

| 항목 | 내용 |
| --- | --- |
| 상태 | 검토 필요. Claude가 쓴 초안이며 사람의 승인 전입니다. |
| 기준 문서 | [프로젝트 로드맵](roadmap.md) 3절, [개발 아키텍처](10-dev-architecture.md), [기능 정의서](03-functional-spec.md) |
| 일정 | 적지 않습니다. 프로젝트 로드맵과 같은 방침입니다. |

### 프로젝트 로드맵과의 관계

두 문서는 층이 다릅니다. 겹치는 내용을 두지 않습니다.

| | [프로젝트 로드맵](roadmap.md) (RM) | 이 문서 (DRM) |
| --- | --- | --- |
| 다루는 것 | 단계 3개, 관문 2개, 요구사항 묶음 | 구현 단위 7개와 만드는 순서 |
| 단위 | 요구사항과 관문 완료 기준 | 코드와 파일 |
| 끝났다는 판정 | 사람이 관문에서 | 스크립트나 화면으로 확인 |

이 문서가 덮는 범위는 **RM 2단계(프로토타입)의 "만드는 것 다섯 가지"**입니다. 그것을 코드 단위로 쪼개고 순서를 붙였습니다. RM 3단계(개발)의 작업 묶음 8개와의 대응은 8절에 있습니다.

## 2. MVP의 정의

MVP는 **파일럿 한 건이 프로젝트 정의서에서 화면설계서까지 완주하는 데 필요한 최소 코드**입니다. 관문 G2의 완료 기준과 같은 선입니다.

파일럿 대상은 이 시스템 자신(UX AI Studio 뷰어)입니다(결정 기록 2026-11-25). 그래서 MVP는 두 가지를 동시에 합니다.

1. 에이전트 파이프라인이 뷰어의 기획 문서를 만든다.
2. 그 문서대로 뷰어를 만든다. 뷰어가 1번의 결과를 보여 준다.

`project-id`는 `ux-ai-studio`를 제안합니다. 이미 쓴 [유저 플로우](04-user-flow.md), [워크 플로우](05-workflow.md), [정보 구조도](06-information-architecture.md), [화면설계서](07-screen-spec.md)가 이 프로젝트의 **기대 결과**이므로, 에이전트가 만든 것과 대조해 품질을 잴 수 있습니다. 이것이 파일럿을 이 시스템으로 고른 이득입니다.

### MVP 밖으로 미루는 것

RM 3절이 개발 단계로 넘긴 것과 같습니다. 코드 단위로 다시 적습니다.

| 미루는 것 | 왜 |
| --- | --- |
| Figma 내보내기와 실제 Figma 추출 | 검증된 화면을 나중에 연결하기로 확정했습니다(결정 기록) |
| 블록 레지스트리의 저장소화와 커넥터 연결 | 1차는 뷰어가 쓰는 블록만 직접 만듭니다(DEV 8절) |
| 예약 작업과 GitHub Actions를 쓰는 자동화 | 리서치 프리뷰에 기대지 않습니다(FSD 7절) |
| 뷰어의 실행 버튼(API 트리거) | 파일럿으로 기본 흐름을 확인한 뒤에 붙입니다 |
| 열려 있는 PR 목록의 실시간 조회 | 1차는 GitHub 링크로 대신합니다(DEV 5.2절) |
| 부분 재생성(FN-407)과 승인 해제(FN-704) | M6에서 영향 분석까지만 하고 재생성은 손으로 지시합니다 |

### M0 저장소 뼈대

파이프라인이 쓸 자리와 검사 수단을 먼저 만듭니다. 에이전트도 뷰어도 아직 없습니다.

| 항목 | 내용 |
| --- | --- |
| 만드는 것 | `schemas/*.schema.json` 9개, `templates/PROJECT.md`, `scripts/check_project.py`, `scripts/lib/`, `projects/ux-ai-studio/` 폴더와 `_meta/status.json` |
| 완료 기준 | 손으로 쓴 `PROJECT.md`·`project.json` 한 쌍이 `check_project.py`를 통과한다. 일부러 틀린 JSON을 넣으면 실패한다. |
| 선행 | 없음 |
| 관련 | REQ-001, REQ-004, REQ-023, DATA 전체 |

데이터 규격 8절이 남긴 미정 사항(우선순위 값, `deprecated` 표시, 파일 공통 머리 필드)을 여기서 확정해야 스키마를 쓸 수 있습니다.

### M1 에이전트 계층

총괄과 전문 에이전트를 저장소 파일로 옮기고, 파이프라인의 앞 두 단계를 돌립니다.

| 항목 | 내용 |
| --- | --- |
| 만드는 것 | `CLAUDE.md`, `.claude/agents/` 6개, `.claude/settings.json`, `scripts/check_gate.py`, `_meta/runs.json` 쓰기 |
| 완료 기준 | `projects/ux-ai-studio/PROJECT.md`를 확정하고 세션에 지시하면, Requirements와 Policy 단계가 돌아 PR 두 개가 열린다. 훅이 `status.json`의 승인 전환과 `origin: human` 항목 덮어쓰기를 실제로 막는다. |
| 선행 | M0 |
| 관련 | REQ-003, REQ-006, REQ-010, REQ-018, FN-401, FN-402, FN-601, FN-603 |

여기서 처음으로 사용량을 잽니다(RM 2단계의 측정 항목). 한 단계를 돌리는 데 얼마나 쓰는지 `runs.json`에 남깁니다.

### M2 파이프라인 완주

남은 생성 단계를 돌려 화면설계서 직전까지 갑니다.

| 항목 | 내용 |
| --- | --- |

| 완료 기준 | 정보 구조도까지 생성되고 참조 검사를 통과한다. `ia.json`의 모든 `SCR`이 작업 단위 하나에 속한다. 사람이 정보 구조도 PR을 병합해 승인한다. |
| 선행 | M1 |
| 관련 | REQ-005, REQ-025, FN-403~405, FN-408 |

생성 결과를 이미 쓴 [정보 구조도](06-information-architecture.md) 0.1.0과 대조합니다. 다르면 어느 쪽이 맞는지 판단해 문서나 에이전트 명세를 고칩니다. **이 대조가 파이프라인 품질의 첫 실측값입니다.**

## 5. 만드는 순서

```
M0 저장소 뼈대
 └─ M1 에이전트 계층 ──────────── (사용량 첫 측정)
     └─ M2 파이프라인 완주 ────── (파이프라인 품질 첫 측정)
         └─ M3 뷰어 뼈대 + WU-001
             ├─ M4 문서·플로우 (WU-002)
             └─ M5 렌더러 (WU-003) ← M4의 블록을 재사용
                 └─ M6 검증·변경 (WU-004)
                     └─ M7 파일럿 완주와 측정 → 관문 G2
```

순서를 이렇게 둔 이유는 세 가지입니다.

- **빌드가 필요 없는 계층을 먼저 만듭니다.** M0~M2에는 뷰어가 없습니다. 파이프라인이 도는지를 React 설정 문제와 섞지 않고 확인합니다(DEV 2절).
- **보여 줄 데이터를 먼저 만듭니다.** M3이 M2 뒤인 이유입니다. 뷰어를 먼저 만들면 가짜 데이터로 화면을 맞추게 되고, 실제 생성 결과가 나왔을 때 다시 고치게 됩니다.
- **작업 단위 순서를 그대로 따릅니다.** M3~M6이 WU-001→004입니다. IA 6절이 "앞의 작업 단위가 공통 요소를 먼저 정하면 뒤가 재사용한다"고 적은 순서와 같습니다.

## 6. 단계마다 무엇으로 확인하는가

"됐다"의 판정을 사람의 느낌에 맡기지 않습니다.

| MVP | 확인 수단 |
| --- | --- |
| M0 | `check_project.py`가 통과하고, 일부러 틀린 입력에서 실패한다 |
| M1 | PR 두 개가 열린다. 훅이 막는 세 가지를 시험으로 재현한다 |
| M2 | 참조 검사 통과. 생성된 `ia.json`과 [정보 구조도](06-information-architecture.md) 0.1.0의 차이 목록 |
| M3 | 화면이 뜬다. SB 2절의 예외 상황 8개 재현. 쓰기 호출 없음 |
| M4 | 참조를 따라 화면을 오간다. PNG 파일이 받아진다 |
| M5 | 렌더러 결과와 손으로 만든 화면의 대조. 인터랙션 동작 |
| M6 | 검증 규칙 7개 판정. 정책 하나를 바꿨을 때의 영향 목록 |
| M7 | 관문 G2의 완료 기준 다섯 가지 |

## 7. 이 순서에 걸린 선결 사항

시작하기 전이나 중간에 막는 것들입니다. 괄호 안이 막는 MVP입니다.

| 선결 사항 | 어디에 있나 | 막는 곳 |
| --- | --- | --- |
| 데이터 규격의 미정 사항(우선순위 값, `deprecated`, 파일 머리 필드) | DATA 8절 | M0 |
| 에이전트 실행 정책 POL-007~012의 확정 | AGT 10절 | M1 |
| 같은 문서의 재실행 횟수 한도 (POL-008) | AGT 10절 | M1 |
| 기술 스택 제안의 확정 | [개발 아키텍처](10-dev-architecture.md) 4절 | M3 |
| 뷰어 배포처와 비공개 저장소의 Pages 가능 여부 | IA 7절, DEV 10절 | M3 |
| 코드 연결 없는 블록의 컴포넌트를 누가 만드는지 | DATA 8절, SB 4절 | M3 |
| SB의 WU-002~004 작성 (WU-001 승인 뒤) | SB 4절 | M4, M5, M6 |
| 문서별 승인 권한자와 브랜치 보호 규칙 | PRJ 11절 | M1 |

맨 아래 두 줄이 중요합니다. **WU-002~004의 화면설계서가 없으면 M4~M6을 시작할 수 없습니다.** 화면설계서를 작업 단위로 쓰기로 한 결정(2026-11-25)의 결과이며, 문서 작성과 구현이 번갈아 갑니다.

## 8. 프로젝트 로드맵의 작업 묶음과의 대응

RM 4절은 개발 단계를 요구사항 기준으로 여덟 묶음으로 나눴습니다. 이 문서의 MVP와 다음과 같이 대응합니다.

| RM 4절의 묶음 | 이 문서의 MVP |
| --- | --- |
| 1 데이터 규격과 검증 스크립트 | M0 |
| 2 에이전트 명세와 총괄 규칙 | M1, M2 |
| 3 뷰어 (UX AI Studio) | M3, M4 |
| 4 UI 블록 라이브러리 연결 | M3의 일부(직접 만드는 블록만). 레지스트리 연결은 MVP 밖 |
| 5 화면설계서 생성과 내보내기 | M5. Figma 내보내기는 MVP 밖 |
| 6 변경 추적과 검증 | M6. 부분 재생성은 MVP 밖 |
| 7 자동화 (선택) | MVP 밖 |
| 8 실제 프로젝트 적용 | MVP 밖. M7은 파일럿까지입니다 |

## 9. 위험

RM 5절의 위험 가운데 구현 순서에 직접 걸리는 것만 적습니다.

| 위험 | 어느 MVP에서 드러나나 | 대응 |
| --- | --- | --- |
| Max 플랜의 사용량 한도로 실행이 멈춘다 | M1부터 | 단계별로 끊어 실행하고 `runs.json`으로 이어 갑니다(POL-029). M1에서 한 단계당 사용량을 재 M2 이후를 계획합니다. |
| 뷰어용 블록이 라이브러리에 없다 | M3 | 뷰어가 쓰는 블록만 직접 만들고 등록 요청을 남깁니다. 요청이 계속 늘면 파일럿 대상을 다시 봅니다. |
| 렌더러 결과가 손으로 만든 화면과 다르다 | M5 | M5의 완료 기준 자체입니다. 다르면 JSON 규격을 고치고 M3의 블록을 다시 봅니다. |
| 빌드 시점 수집의 갱신 지연이 쓰기 어렵다 | M3 | 파일 접근을 `data/load.ts`에 가뒀으므로 런타임 조회로 바꿀 때 고칠 파일이 하나입니다(DEV 5.2절). |
| 생성 품질이 기대에 못 미친다 | M2 | 이미 쓴 문서와 대조해 차이를 수치로 냅니다. 에이전트 명세를 고치는 것이 1차 대응이고, 그래도 안 되면 관문 G2에서 방향을 다시 정합니다. |
