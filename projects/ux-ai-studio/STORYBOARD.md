# 화면설계서: UX AI Studio

> **Screen Agent가 만든 초안입니다. 사람의 승인 전입니다.**
> 승인은 사람이 PR을 병합할 때만 일어납니다(POL-002, 시스템 규칙). 이 판은 **WU-001 프로젝트와
> 진행 현황**, **WU-002 문서와 플로우 보기**, **WU-003 화면설계서 보기**, **WU-004 검증과 변경

## 1. 문서 개요

이 문서는 작업 단위 WU-001, WU-002, WU-003, WU-004에 속한 화면 일곱 장의 설계입니다. 화면마다 영역을
나누고, 영역마다 UI 블록·요구사항·정책·디스크립션·인터랙션·예외를 연결했습니다. 작업 단위는 한 번에
하나씩 쓰며, 앞선 작업 단위가 정한 공통 요소를 뒤가 그대로 받아 씁니다(정보 구조도 6절).

화면의 덩어리와 영역 구성은 저장소의 [화면설계서](../../docs/07-screen-spec.md)가 같은 뷰어를
`STU-01`, `STU-02`로 설계해 둔 것을 근거로 삼았습니다. 다만 거기에 적힌 정책 ID는 **이 시스템
자체의 정책**이고, 이 문서가 연결한 정책 ID는 **이 프로젝트의 [정책서](POLICY.md)(POL-001~021)**
입니다. 두 체계가 번호만 같고 내용이 달라, 영역마다 프로젝트 정책서를 다시 읽고 연결했습니다.

WU-002의 화면 둘(SCR-003, SCR-004)은 저장소의 화면설계서에 대응하는 화면이 없습니다. 그래서
[정보 구조도](IA.md) 2·3절의 화면과 이동, [유저 플로우](USER-FLOW.md) UF-012~UF-018,
[워크 플로우](WORKFLOW.md) WF-012~WF-018만 근거로 삼았고, 공통 요소(글로벌 헤더, 상태 배지,
바깥 링크 버튼, 빈 상태)는 WU-001에서 정한 것을 그대로 받아 썼습니다.

WU-003의 화면 하나(SCR-005)도 마찬가지로 저장소의 화면설계서에 대응하는 화면이 없습니다.
근거는 [유저 플로우](USER-FLOW.md) UF-019~UF-023과 UF-030, [워크 플로우](WORKFLOW.md)
WF-019~WF-023과 WF-030, [정보 구조도](IA.md) 2·3절의 이동 'SCR-005 → SCR-003'입니다. 공통 요소는
WU-001에서, 항목 ID 배지와 참조 줄·내보내기 처리는 WU-002에서 정한 것을 그대로 받아 썼습니다.
**이 화면이 그릴 입력은 이 문서가 만든 화면 파일 자체입니다.** 그래서 6절은 `screens/SCR-000.json`의
구조([데이터 규격](../../docs/08-data-spec.md) 4절)를 화면의 요구로 그대로 받았습니다.

WU-004의 화면 둘(SCR-006, SCR-007)도 저장소의 화면설계서에 대응하는 화면이 없습니다. 근거는
[유저 플로우](USER-FLOW.md) UF-024~UF-027과 완료 단계 UF-031, [워크 플로우](WORKFLOW.md)
WF-024~WF-027과 WF-031, [정보 구조도](IA.md) 2·3절의 이동 다섯('SCR-006 → SCR-003',
'SCR-006 → SCR-005', 'SCR-006 → SCR-007', 'SCR-006 → SCR-002', 'SCR-007 → SCR-003')입니다.
**이 둘은 보내는 화면입니다.** 앞선 작업 단위가 만든 화면(SCR-002, SCR-003, SCR-005)으로 사람을
보내므로, 받는 쪽이 이미 정해 둔 상태를 그대로 맞췄습니다. 특히 실패 항목이 영역 ID
(`SCR-000-A00`)일 때는 SCR-005-A02가 정한 대로 그 영역을 고른 채로 엽니다. 두 화면이 그릴 입력은
[데이터 규격](../../docs/08-data-spec.md) 4절의 `validation.json`과 5절의 `_meta/changes.json`이며,
7·8절은 그 두 스키마의 필드를 화면의 요구로 그대로 받았습니다.

### props 표기 규칙

`props`의 키는 블록의 React 컴포넌트 prop 이름을 그대로 씁니다(POL-026, 시스템 규칙). 한글 슬롯
이름은 쓰지 않습니다. 값은 이렇게 적었습니다.

| 값의 모양 | 뜻 | 예 |
| --- | --- | --- |
| 문자열·불리언·숫자 | 화면에 그대로 보이는 값 | `"title": "프로젝트"`, `"showSearch": true` |
| state 키 이름 문자열 | 그 화면 `state`의 값에서 온다 | `"items": "projects"` |
| state 키 이름 문자열(콜백 prop) | 눌렀을 때 그 state 키를 바꾼다 | `"onSelect": "selectedProjectId"` |
| state 키 이름 문자열의 배열 | 묶음 여럿을 차례로 받는다. WU-002에서 처음 썼습니다 | `"groups": ["parentRefs", "childRefs"]` |
| state 키가 아닌 핸들러 이름 | 화면 밖으로 나가거나 다른 화면으로 가는 동작. 이 화면의 state를 바꾸지 않습니다 | `"onSelect": "openPolicyItem"` |
| 문자열의 배열 | 묶음마다 다른 고정 문구. WU-003에서 처음 썼습니다 | `"emptyMessages": ["적힌 디스크립션이 없습니다", "적힌 예외가 없습니다"]` |

## 2. SCR-001 프로젝트 목록

뷰어의 입구입니다. 저장소의 `projects/` 아래 폴더를 읽어 카드로 보여 주고, 카드를 누르면
진행 현황(SCR-002)으로 갑니다.

```json
{
  "id": "SCR-001",
  "refs": ["UF-001", "UF-002", "UF-003", "UF-004", "UF-005", "UF-033", "WF-001~005", "WF-033"],
  "state": { "keyword": "", "projects": [], "selectedProjectId": null, "repoReadAt": null }
}
```

| 영역 | 이름 | 블록 | props | 요구사항 | 정책 |
| --- | --- | --- | --- | --- | --- |
| SCR-001-A01 | 글로벌 헤더 | BLK-0001 `^2` | `logo`, `title`, `showBack`, `showSearch`, `actions`, `readAt`, `onRefresh` | REQ-001, REQ-020 | POL-004, POL-001 |
| SCR-001-A02 | 프로젝트 카드 목록 | BRQ-0001 `^0` (등록 요청) | `items`, `onSelect`, `keyword` | REQ-001, REQ-002, REQ-020 | POL-008, POL-005, POL-004 |
| SCR-001-A03 | 빈 상태 | BLK-0012 `^1` | `illustration`, `title`, `description`, `action` | REQ-001, REQ-019 | POL-008, POL-020 |
| SCR-001-A04 | 바깥으로 나가는 버튼 | BLK-0003 `^2` | `primaryAction`, `secondaryAction`, `disabled` | REQ-004, REQ-015 | POL-003, POL-001 |

**디스크립션에서 짚을 것**

- A01: 입구라 뒤로가기를 두지 않습니다. 검색은 이미 읽어 둔 프로젝트의 **이름만** 거릅니다.
  **헤더 오른쪽에 저장소를 읽은 시점과 새로고침을 둡니다**(POL-004). 읽은 시점은 뷰어가 저장소를
  읽어 온 시각이고(날짜만이 아니라 시각까지 보입니다), 다시 읽기는 새로고침으로만 합니다. 저절로
  다시 읽지 않습니다. **이 자리를 여기서 정하고 나머지 여섯 화면의 헤더가 그대로 받아 씁니다.**
  새로고침은 읽기만 하고 저장소에 아무것도 쓰지 않습니다(POL-001).
- A02: 카드의 모든 값은 `_meta/status.json`에서 읽습니다. 진행 상태 배지는 POL-005의 다섯 값만
  씁니다. **이 배지의 모양을 여기서 정하고 SCR-002와 뒤의 작업 단위가 그대로 받아 씁니다.**
- A03: A02를 대신해 보입니다. 둘이 같이 보이지 않습니다. 권한이 없어 비어 보이는 경우와 폴더가
  정말 없는 경우를 문구로 구분합니다.
- A04: 주 버튼은 claude.ai/code 세션을, 보조 버튼은 GitHub 저장소를 새 탭으로 엽니다. 뷰어는
  프로젝트를 만들지 않습니다.

**인터랙션**

| 영역 | 트리거 | 바꾸는 state | 결과 |
| --- | --- | --- | --- |
| A01 | 검색어를 입력한다 | `keyword` | A02의 카드를 이름으로 거릅니다. 결과가 없으면 A03이 보입니다. |
| A01 | 우측 액션을 누른다 | 없음 | GitHub 저장소를 새 탭으로 엽니다. |
| A01 | 새로고침을 누른다 | `repoReadAt` | `projects/` 아래의 폴더와 `_meta/status.json`을 다시 읽고 읽은 시점을 지금으로 바꿉니다. |
| A01 | 화면을 처음 읽어 들인다 | `repoReadAt` | 저장소를 읽은 시각을 읽은 시점 자리에 보입니다. |
| A02 | 프로젝트 카드를 누른다 | `selectedProjectId` | SCR-002로 갑니다. |
| A02 | 검색어가 바뀐다 | `keyword` | 이름이 검색어를 품은 카드만 남습니다. |
| A03 | 다음 행동 버튼을 누른다 | 없음 | GitHub 저장소를 새 탭으로 엽니다. |
| A04 | 주 버튼 / 보조 버튼을 누른다 | 없음 | 세션 / GitHub을 새 탭으로 엽니다. |

**예외 상황**

정책에 적힌 예외를 영역의 `exceptions`에 그대로 옮겼습니다(QA-05). 아래는 그 밖에 이 화면에서
더 적은 것입니다.

| 상황 | 화면 | 근거 |
| --- | --- | --- |
| `_meta/status.json`을 읽지 못했다 | 카드 자체는 보이고 진행 상태 자리에만 '읽지 못했습니다'와 경로를 보입니다 | POL-004, UF-035 |
| 검색 결과가 없다 | A03의 제목을 '검색 결과가 없습니다'로 바꾸고 검색어를 지우는 안내를 보입니다 | BLK-0012의 '검색 결과 없음' 변형 |
| 볼 수 있는 프로젝트가 없다 | A03만 보이고 다른 화면으로 가지 않습니다 | POL-008, POL-020, UF-033 |
| 읽은 시점이 비어 있다 | 헤더에 '읽은 시점 없음'을 보이고 시각을 지어내지 않습니다. 새로고침은 그대로 누를 수 있습니다 | POL-004 |
| 새로고침이 실패했다 | 앞서 읽은 값과 읽은 시점을 그대로 두고 헤더에 '다시 읽지 못했습니다'를 보입니다 | POL-004 |

**읽은 시점과 새로고침은 일곱 화면이 모두 씁니다.** 위의 예외 둘도 헤더를 쓰는 영역
(SCR-001-A01 ~ SCR-007-A01) 일곱 곳에 같은 문장으로 들어 있습니다. 3~8절에서는 다시 적지 않습니다.

## 3. SCR-002 프로젝트 진행 현황

- A02: 확정 대기·승인 대기·선택 대기를 한 줄로 먼저 보입니다. 둘 이상이면 앞선 단계의 것 하나를
  먼저 보이고 나머지는 펼쳐서 봅니다(POL-007). 승인 버튼이나 실행 버튼을 뷰어에 두지 않습니다.
  **기다리는 일이 하나도 없으면 줄 자체가 사라집니다.** 이 줄만 BRQ-0005를 씁니다.
- A03: 수치 셋(끝난 단계, 검토 중 단계, 만들어진 문서)은 모두 `_meta/status.json`과 폴더의 파일

- A04: 단계 일곱의 순서를 바꾸지 않습니다. **플로우 단계는 유저 플로우와 워크 플로우를 한 칸으로
  묶고, 두 문서의 상태가 다르면 뒤처진 쪽을 단계 상태로 삼습니다**(POL-006). 앞뒤는 POL-005의
  다섯 값을 **'대기 → 수정 필요 → 생성 중 → 검토 필요 → 승인'** 순으로 보고 이 차례에서 앞에
  오는 쪽이 뒤처진 쪽입니다. 유저 플로우가 '승인'이고 워크 플로우가 '검토 필요'이면 배지는
  '검토 필요'입니다. 펼치면 두 문서의 상태가 따로 나오고, 어느 한쪽을 감추지 않습니다.
  화면설계서 단계는 작업 단위마다 상태를 따로 가지며, 배지는 가장 뒤처진 작업 단위의 상태를
  보이고 펼치면 작업 단위별 상태가 나옵니다. **한 단계에 상태가 셋 이상 묶여도 같은 차례에서
  가장 앞에 오는 것을 단계 상태로 삼습니다**(POL-006의 조건). 이 차례는 **정책서 0.2.0이
  POL-005의 조건에 적은 것**이며, 0.6.0에서 이 화면이 임의로 정했던 것을 0.6.1에서 맞췄습니다.
- A05: '문서 보기'가 어느 화면으로 갈지는 **문서 코드**로 정합니다(WF-011). 문서는 SCR-003,
  플로우는 SCR-004, 화면설계서는 SCR-005, 검증은 SCR-006입니다.
- A06: 이 프로젝트 폴더를 건드리는 열린 PR만 보입니다. 승인은 GitHub에서 합니다.
- A07: `_meta/changes.json`에 승인된 항목의 변경이 있으면 요약 수치 위에 한 줄로 보이고 SCR-007로
  보냅니다. 변경 기록이 없으면 '변경이 없습니다'로 흐리게 보이고 누를 수 없습니다. **변경이 없어도
  줄은 남습니다.** A02와 묶지 않고 **독립된 영역·블록(BRQ-0006)**으로 둡니다. 이 영역의 근거는
  정보 구조도 3절의 이동 `SCR-002 → SCR-007`이고 **유저 플로우에는 대응하는 단계가 없습니다.**
  대응 단계를 플로우에 만들지 않고 이 영역을 따로 그리기로 2026-11-26에 **확정했습니다.**

## 4. SCR-003 문서 보기

요구사항·정책·정보 구조도처럼 항목 목록으로 읽는 산출물을 항목 단위로 읽습니다. 항목을 고르면
그 항목이 참조하는 상위 항목과 그 항목을 참조하는 하위 항목이 옆에 나오고, 어느 쪽으로든 눌러서
옮겨 갑니다. 참조를 따라 플로우 미리보기(SCR-004)와 화면설계서 뷰어(SCR-005)로 나갑니다.

```json
{

  "state": {
    "docs": [], "docCode": "REQ", "items": [], "selectedItemId": null,
    "parentRefs": [], "childRefs": [], "visitedTrail": [], "repoReadAt": null
  }
}
```

**UF-036·UF-038은 유저 플로우 0.3.0이 더한 단계입니다.** UF-036은 '참조를 따라 다른 산출물의
보기 화면으로 옮겨 간다'이고 A04가 그 자리이며, UF-038은 '문서 보기에서 진행 현황으로
돌아간다'이고 A01의 뒤로가기가 그 자리입니다. 0.5.1까지는 둘 다 플로우에 단계가 없다고 보고
적지 않았습니다.

## 6. SCR-005 화면설계서 뷰어

화면설계서 JSON을 동작하는 화면으로 그립니다. 영역을 고르면 그 영역의 디스크립션과 예외를 화면
옆에 나란히 읽고, 걸린 요구사항·정책 ID를 눌러 문서 보기(SCR-003)로 갑니다. 화면이 쓴 블록은
라이브러리 블록·등록 요청 중인 블록·알 수 없는 블록 셋으로 갈라 보이고, 보고 있는 화면설계서를
PPTX 파일 하나로 내려받습니다.

```json
{
  "id": "SCR-005",
  "refs": ["UF-019", "UF-020", "UF-021", "UF-022", "UF-023", "UF-030", "UF-040",
           "WF-019~023", "WF-030", "WF-040"],
  "state": {
    "screens": [], "screenId": null, "screenAreas": [], "selectedAreaId": null,
    "previewState": {},
    "areaDescription": [], "areaExceptions": [], "areaRequirements": [], "areaPolicies": [],
    "libraryBlocks": [], "requestedBlocks": [], "unknownBlocks": [],
    "exportState": "대기", "repoReadAt": null
  }
}
```

**UF-040·WF-040은 유저 플로우 0.3.0이 더한 단계입니다.** '화면설계서 뷰어에서 진행 현황으로
돌아간다'이며 A01의 뒤로가기가 그 자리입니다. 헤더가 공통으로 받은 `repoReadAt`까지 더해
state 키는 열셋에서 열넷이 되었습니다.

state 키가 열셋으로 앞의 화면보다 많습니다. 그릴 화면을 고르는 둘(`screens`, `screenId`), 그린
결과와 고른 영역 둘(`screenAreas`, `selectedAreaId`), 고른 영역에서 꺼낸 넷(`areaDescription`,
`areaExceptions`, `areaRequirements`, `areaPolicies`), 블록을 세 갈래로 가른 셋, 내보내기 하나입니다.
**`previewState`만 성격이 다릅니다.** 그려진 화면 안에서 눌러 보는 인터랙션이 쓰는 state이고,
화면 파일의 `state`를 그대로 읽어 만듭니다(WF-019). 뷰어 자신의 state와 섞지 않습니다.
열넷째인 `repoReadAt`은 뷰어 자신의 것이며 그려진 화면의 state가 아닙니다.

**디스크립션에서 짚을 것**

- A01: 헤더는 SCR-001-A01에서 정한 모양을 그대로 받아 씁니다. **읽은 시점과 새로고침도 같이
  받습니다**(POL-004). 이 화면에서는 보고 있는 화면 파일을 읽은 시각을 보이고, 새로고침은 그
  파일을 다시 읽어 와이어프레임을 새로 그립니다. 타이틀은 보고 있는 화면의 ID와 이름이고
  뒤로가기는 진행 현황(SCR-002)으로 돌아갑니다(UF-040). **영역을 거르는 검색을 두지 않습니다.**
  영역은 화면 파일에 적힌 순서 그대로 그려야 합니다(POL-014).
- A02: 화면설계서에 있는 화면(SCR)을 탭으로 바꿔 봅니다. 탭은 **작업 단위로 묶어** 보이고 묶음
  머리에 작업 단위 ID와 이름이, 탭마다 SCR-001-A02에서 정한 상태 배지가 붙습니다. 작업 단위별
  진행 상태를 여기서 다시 세지 않습니다. 그것은 SCR-002-A04가 맡습니다. **문서 보기(SCR-003)의
  참조 패널에서 들어오면** 그 화면의 탭을 열고, 들어온 ID가 영역 ID(`SCR-000-A00`)면 그 영역을
  고른 채로 엽니다. WU-002가 넘긴 사항(11절)에 대한 답입니다.
- A03: 화면 파일의 `areas`를 적힌 순서대로 React 컴포넌트로 그리고, 영역의 `interactions`에 적힌
  것을 눌러 볼 수 있게 합니다. 누르면 `previewState` 안의 키가 바뀌고 결과가 화면에 나타납니다.
  서버 없이 React State로만 돕니다(REQ-017). **블록을 그리지 못한 영역은 건너뛰지 않습니다.**
  그 자리에 '블록을 그리지 못했습니다'와 블록 ID를 보이고 나머지 영역은 그대로 그리며, 그 영역도
  고를 수 있어 디스크립션과 예외는 읽힙니다(POL-014).
- A04: 고른 영역의 디스크립션과 예외를 **접지 않고 나란히** 보입니다(POL-015). 문장은 화면 파일의
  `description`과 `exceptions`를 적힌 순서 그대로이며 뷰어가 요약하지 않습니다. 묶음마다 빈 자리
  문구가 다릅니다('적힌 디스크립션이 없습니다' / '적힌 예외가 없습니다').
- A05: 고른 영역에 걸린 요구사항과 정책을 묶음 둘로 보이고, ID를 누르면 문서 보기(SCR-003)의 그
  항목으로 갑니다. 정보 구조도 3절의 이동 'SCR-005 → SCR-003'이 이 자리입니다. **SCR-003-A04,
  SCR-004-A04와 같은 블록(BRQ-0008)을 씁니다.** 다시 쓴 근거는 9절에 적었습니다.
- A06: 화면이 쓴 블록을 영역마다 한 줄로 보이고 **라이브러리 블록 · 등록 요청 중인 블록 · 알 수
  없는 블록** 셋으로 갈라 보입니다(POL-016). 줄에는 블록 ID와 Major 버전 범위, 그 블록을 쓴 영역이
  있습니다. 줄을 누르면 화면을 옮기지 않고 A03에서 그 영역을 고릅니다. 블록 하나를 자세히 보는
  화면은 뷰어에 없습니다.
- A07: 주 버튼이 PPTX 내보내기입니다. **내보내는 단위는 화면설계서 하나이고 보고 있는 화면 한
  장이 아닙니다.** 화면 한 장이 장표 한 장이고 그려진 화면과 영역별 디스크립션을 같이
  담습니다(REQ-012, WF-022). 그리지 못한 영역도 **비우지 않고 표시해 담습니다**(POL-017).
  보조 버튼은 세션을 엽니다. A06의 알 수 없는 블록을 세션에 알리는 자리이며 유저 플로우의
  이탈(UF-021 → UF-032)이 여기서 일어납니다.
- A08: 내보내기 결과를 A07 아래 한 줄로 보입니다. 상태는 WF-023이 판정한 '내려받음',
  '내보내지 못함', '내보낼 것 없음' 셋이고 누르기 전에는 줄을 보이지 않습니다. **SCR-004-A07과

## 7. SCR-006 검증 결과

검증 규칙 일곱(QA-01~QA-07)의 통과와 실패를 한 화면에서 봅니다. 실패한 규칙의 항목 ID를 눌러
고칠 곳으로 옮겨 가고, 규칙마다 **누구를 다시 불러야 하는지**를 `validation.json`의 `owner_agent`
그대로 보입니다. 등록 요청 중인 블록을 쓴 영역은 따로 표시합니다(QA-07). 뷰어는 다시 판정하지
않습니다. 파일에 적힌 판정을 그대로 보입니다(REQ-020, POL-004).

```json
{
  "id": "SCR-006",
  "refs": ["UF-024", "UF-025", "UF-026", "UF-042", "WF-024", "WF-025", "WF-026", "WF-042"],
  "state": {
    "summary": [], "rules": [], "selectedRuleId": null,
    "ruleDetail": null, "ruleVerdict": null, "ruleLinks": [],
    "docTargets": [], "screenTargets": [],
    "libraryBlocks": [], "requestedBlocks": [], "unknownBlocks": [],
    "changeNotice": null, "repoReadAt": null
  }
}
```

state 키가 열둘입니다. 요약 수치 하나, 규칙 목록과 고른 규칙 둘, 고른 규칙에서 꺼낸 셋
(`ruleDetail`, `ruleVerdict`, `ruleLinks`), 실패 항목을 가는 곳으로 가른 둘(`docTargets`,
`screenTargets`), 블록을 세 갈래로 가른 셋, 변경 영향 알림 하나입니다. 여기에 헤더가 공통으로
받은 `repoReadAt`이 더해져 열셋이 되었습니다.

**UF-042·WF-042는 유저 플로우 0.4.0이 더한 단계입니다.** '검증 결과에서 진행 현황으로
돌아간다'이며 A01의 뒤로가기가 그 자리입니다. 0.6.0까지 이 화면은 **일곱 장 가운데 혼자 머리의
되돌아가기에 대응 UF를 적지 못했고**, 11절 끝에 "SCR-006의 되돌아가기는 UF-025로 이미 있다"고
적었던 것이 **틀렸습니다.** UF-025의 '결과 없음' 갈래는 사용자가 머리를 누른 것이 아니라 뷰어의
판정이고 결과가 있을 때는 일어나지도 않습니다. 둘은 다른 길이며 A01(UF-042)과 A07(UF-025)로
자리도 다릅니다.

**디스크립션에서 짚을 것**

- A01: 헤더는 SCR-001-A01에서 정한 모양을 그대로 받아 씁니다. **읽은 시점과 새로고침도 같이
  받습니다**(POL-004). 이 화면에서는 `validation.json`을 읽은 시각을 보이고, **새로고침은 파일을
  다시 읽기만 합니다. 검증을 다시 돌리지 않습니다**(REQ-015). 뒤로가기는 진행 현황(SCR-002)으로
  돌아갑니다(**UF-042**). 고른 규칙과 실패 항목 표시는 화면을 떠나면서 버립니다(WF-042).
  **규칙을 거르는 검색을 두지 않습니다.** 규칙은 일곱뿐이고 파일에 적힌 순서를
  그대로 보여야 합니다(REQ-020).
- A02: 수치 셋은 통과 규칙 수, 실패 규칙 수, 요구사항 반영률입니다. 반영률은 QA-01 줄의 `metric`을
  그대로 보이며 뷰어가 다시 계산하지 않습니다. 나머지 여섯 규칙에는 `metric`이 없어 그 자리를
  채우지 않습니다.
- A03: 규칙 일곱을 한 줄기로 늘어놓고 줄마다 **규칙 ID 배지 · 확인 내용 · 판정 배지 · 실패 항목
  수**를 보입니다. 판정은 '통과'와 '실패' 둘뿐입니다(POL-018). 실패를 위로 끌어올리지 않고 파일
  순서를 지킵니다. 누르면 화면을 옮기지 않고 A04·A05가 그 규칙의 것으로 바뀝니다.
- A04: **누구를 다시 불러야 하는지를 이 카드가 보입니다.** `owner_agent`를 '넘길 담당: Screen
  Agent'처럼 그대로 보이고, 그 담당을 다시 부르는 세션 링크와 그 산출물의 PR 링크를 함께 둡니다.
  카드 안에 **검증을 다시 돌리는 버튼도 승인 버튼도 두지 않습니다**(REQ-015, REQ-016, POL-002).
- A05: 고른 규칙의 `targets`를 묶음 둘(문서 항목 / 화면·영역)로 보입니다. 문서 항목 줄은
  SCR-003으로, 화면 줄은 SCR-005로 갑니다. **영역 ID(`SCR-000-A00`)면 그 영역을 고른 채로
  엽니다.** WU-003이 SCR-005-A02에서 정한 받는 쪽 약속을 그대로 지킨 자리입니다. 저장소에 없는
  ID는 끊긴 참조로 두고 누를 수 없게 합니다(POL-011, POL-018).
- A06: **QA-07이 따로 표시한 것을 그리는 자리입니다.** 화면설계서가 쓴 블록을 라이브러리 · 등록
  요청 · 알 수 없음 셋으로 갈라 보이고 줄마다 블록 ID와 Major 버전 범위, 그 블록을 쓴 영역을

  실제로 뜹니다. 등록 요청은 실패가 아니라 '승인 전이라 따로 표시하는 것'이며 묶음을 접지

  레지스트리를 다시 뒤져 판정하지 않습니다.** 이 점이 SCR-005-A06과 다릅니다.
- A07: A02~A06을 대신해 보입니다. 검증을 아직 돌리지 않았을 때입니다. **'검증 실행' 버튼을 두지
  않고**(REQ-015) 진행 현황(SCR-002)으로 돌려보냅니다. UF-025의 셋째 갈래(결과 없음 → UF-006)가
  이 자리입니다.

## 8. SCR-007 변경 영향

승인된 항목이 무엇이 바뀌었고 그 때문에 어디가 '수정 필요'·'검토 필요'인지를 변경마다 봅니다.
영향받는 항목을 누르면 문서 보기(SCR-003)로 가고, **검증 실패 항목과 변경 영향 항목을 한자리에
모아 고쳐야 할 곳을 추려 냅니다**(UF-031). 유저 플로우가 여기서 끝납니다. 고치는 일은 세션이나
GitHub에서 합니다.

```json
{
  "id": "SCR-007",
  "refs": ["UF-027", "UF-031", "UF-041", "WF-027", "WF-031", "WF-041"],
  "state": {
    "summary": [], "changes": [], "selectedChangeId": null,
    "needsFix": [], "needsReview": [],
    "failedTargets": [], "impactedTargets": [], "repoReadAt": null
  }
}
```

state 키가 일곱입니다. 요약 수치 하나, 변경 목록과 고른 변경 둘, 고른 변경의 영향을 판정으로 가른
둘(`needsFix`, `needsReview`), 고칠 곳 목록을 온 곳으로 가른 둘(`failedTargets`,
`impactedTargets`)입니다. **뒤의 둘만 고른 변경과 무관합니다.** 모든 변경과 검증 결과 전체를
모은 목록이기 때문입니다(WF-031). 여기에 헤더가 공통으로 받은 `repoReadAt`이 더해져 여덟이
되었습니다.

**UF-041·WF-041은 유저 플로우 0.3.0이 더한 단계입니다.** '변경 영향에서 진행 현황으로
돌아간다'이며 A01의 뒤로가기가 그 자리입니다. 검증 결과(SCR-006)에서 들어왔어도 같은 자리로
돌아간다는 것까지 플로우가 적고 있습니다.

**디스크립션에서 짚을 것**

- A01: 헤더는 SCR-001-A01에서 정한 모양 그대로입니다. **읽은 시점과 새로고침도 같이
  받습니다**(POL-004). 이 화면에서는 `_meta/changes.json`과 `validation.json`을 읽은 시각을
  보이고, 새로고침은 둘을 다시 읽기만 합니다. 뷰어가 판정을 다시 매기지 않습니다.
  **검증 결과(SCR-006)에서 들어왔어도 뒤로가기는 진행 현황(SCR-002)으로 갑니다**(UF-041).
  진행 현황이 산출물을 고르는 허브이기 때문이며, WU-002가 넘긴 '진행 현황으로 돌아가는 공통
  경로'를 같은 방식으로 이었습니다.
- A02: 수치 셋은 변경 건수, '수정 필요' 수, '검토 필요' 수입니다. 변경마다의 `impact` 줄을 판정별로
  센 값이며 **뷰어가 판정을 매기지 않습니다**(POL-019, POL-004).
- A03: 줄마다 **바뀐 항목의 ID 배지 · 이전 값과 새 값 · 바꾼 주체 · 커밋 해시**를 보입니다. 바꾼
  주체는 `_meta/changes.json`의 `by`이고 사람이면 GitHub 사용자, 에이전트면 에이전트 이름인
  **문자열 하나**입니다(데이터 규격 5절). **그 값을 줄 안에 글자 그대로 보이고 사람인지
  에이전트인지 뷰어가 가르거나 추측하지 않습니다.** 그래서 `showOrigin`을 **거짓**으로 두고
  **POL-009를 이 영역에 걸지 않습니다.** 순서는 파일에 적힌 순서 그대로이고 최근 것을 위로
  끌어올리지 않습니다. 누르면 A04가 그 변경의 것으로 바뀝니다. **SCR-003-A03과 같은
  블록(BRQ-0007)을 씁니다.** props의 키 묶음도 같고 `showOrigin`의 값만 다릅니다.

> **0.6.0에서 고친 것(QA-02 1번).** 0.5.1까지 이 영역은 POL-009를 걸고 `showOrigin`을 참으로
> 두었습니다. POL-009가 가르는 값은 `'ai'`와 `'human'` 둘인데 `by`는 자유 문자열이라, 정책대로
> 그리면 구분 표시가 영영 뜨지 않고 디스크립션대로 그리면 정책의 예외를 어기는 모순이
> 있었습니다. **2026-11-27에 사람이 화면을 고치는 쪽으로 정했습니다.** `changes.json`에 `origin`을
> 더하지 않고 정책서도 고치지 않았습니다. POL-009는 '문서는 항목 단위로 보이고 출처를
> 구분한다'인데 변경 기록은 문서의 항목이 아니므로 애초에 걸릴 자리가 아니었다는 것이 근거이고,
> 변경 줄을 어떻게 보일지는 POL-019가 정합니다. 영역의 정책은 POL-019·POL-004 둘이 남습니다.
> 예외에서도 POL-009에서 온 둘("문서는 있으나 항목이 하나도 없으면 '항목이 없습니다'를 보인다",
> "출처 값이 'ai'도 'human'도 아니면 구분 표시 없이 본문만 보인다")을 거두고, 대신 "바꾼
> 주체(`by`)가 비어 있으면 그 자리에 '비어 있음'을 보이고 사람인지 에이전트인지 추측하지
> 않는다"를 넣었습니다.
- A04: 고른 변경의 `impact`를 묶음 둘로 보입니다. 위가 '수정 필요', 아래가 '검토 필요'이고 판정은
  이 둘뿐입니다(POL-019, 데이터 규격 5절). 데이터 규격 5절이 이 판정의 근거로 적은 POL-018은
  **시스템 규칙**의 번호이고, 이 프로젝트에서 판정 둘을 정한 것은 POL-019입니다.
  **판정을 줄마다 배지로 붙이지 않고 묶음으로 가릅니다.**
  묶음 머리가 판정과 건수를 보입니다. 줄을 누르면 SCR-003으로 가고 끊긴 참조는 누를 수
  없습니다(POL-011). **SCR-003-A04, SCR-004-A04, SCR-005-A05, SCR-006-A05와 같은
  블록(BRQ-0008)을 씁니다.**
- A05: **흐름이 끝나는 자리입니다**(UF-031). 묶음 둘은 검증 실패에서 온 것(`validation.json`의
  `targets`)과 변경 영향에서 온 것(`changes.json`의 `impact`)이고, 줄마다 어디서 왔는지와
  판정('실패' / '수정 필요' / '검토 필요')을 보입니다. **줄마다 바깥으로 가는 링크 둘**을 붙입니다
  (WF-031). 같은 항목이 양쪽에 들면 합치지 않고 그대로 둡니다. 어느 쪽에서 왔는지가 고칠
  까닭이기 때문입니다.
- A06: A02~A04를 대신해 보입니다. **변경이 없어도 A05는 남습니다.** 검증 실패에서 온 묶음이 있을
  수 있기 때문입니다. 빈 상태의 모양은 SCR-001-A03에서 정한 것을 그대로 받아 씁니다.
- A07: A05의 줄마다 붙는 링크가 항목 하나를 가리킨다면, 이 버튼은 추려 낸 목록 전체를 들고 나가는
  자리입니다. 흐름은 여기서 끝납니다(UF-031 → UF-032). **승인 버튼을 두지 않습니다**(REQ-016,
  POL-002).

## 9. 화면에서 쓰는 UI 블록

Core 가이드, 표준 블록 순으로 찾았습니다(POL-022, 시스템 규칙). 고른 근거는 블록의 "쓰는 상황"과
"쓰지 않을 때"입니다. 쓴 블록 다섯은 모두 `guidance._source`가 `human`이고 `pending_ai_draft`가
`false`라 근거로 쓸 수 있습니다. 폐기된 블록은 쓰지 않았습니다. WU-002와 WU-003에서 쓴 곳을 같은
표에 이어 적었습니다. **WU-003과 WU-004는 새 라이브러리 블록을 한 개도 더하지 않았습니다.**
와이어프레임 렌더링, 영역 하이라이트, 블록 참조 표시, 판정 배지가 붙은 줄처럼 이 뷰어에만 있는
자리는 커머스 목업 25개에 짝이 없어 등록 요청으로 갔습니다(아래).

#### BLK-0001에 '읽은 시점'과 '새로고침'을 더하기로 한 근거 (BRQ-0016)

POL-004의 조건 "화면은 저장소를 읽은 시점을 함께 보이고, 다시 읽기는 새로고침으로 한다"를 그릴
자리가 화면 일곱 장 어디에도 없었습니다(QA-02 2번). **공통 헤더에 자리를 하나 만들면 일곱 장이
모두 받으므로** 헤더에 두기로 했고, SCR-001-A01에서 정해 나머지 여섯이 받아 쓰는 이 문서의 기존
방식을 따랐습니다(11절의 '공통 영역(글로벌 헤더)의 소유').

그런데 **BLK-0001 2.1.0의 슬롯은 로고·뒤로가기·타이틀·우측 액션·검색 다섯뿐이고**
(`code.props`는 `logo`, `showBack`, `title`, `actions`, `showSearch`), 읽은 시점을 보이거나
다시 읽기를 거는 자리가 없습니다. 레지스트리는 읽기만 할 수 있어 블록을 고칠 수 없습니다. 길
셋을 견주었습니다.

| 길 | 어떻게 되는가 | 판단 |
| --- | --- | --- |
| (가) 있는 prop에 끼워 넣는다 | `actions`는 Figma 명세가 `TEXT` 한 칸입니다. 거기에 시각과 저장소 링크와 다시 읽기를 함께 담으면 **읽기 전용 텍스트 슬롯에 조작을 섞는 것**이 됩니다. 새로고침은 누르는 자리라 텍스트로 적을 수 없습니다 | **쓰지 않습니다.** 블록의 명세를 어기고, 화면 파일의 props가 실제 컴포넌트와 달라집니다(POL-026) |
| (나) 머리 아래에 영역을 따로 둔다 | 화면 일곱 장마다 새 영역이 하나씩 생겨 영역이 48개에서 55개가 됩니다. 머리와 본문 사이에 줄이 하나 더 생기고, 뒤로가기·타이틀과 떨어진 자리에 시각이 놓입니다 | **쓰지 않습니다.** 영역 ID 48개를 그대로 두라고 받았고, 헤더에 있어야 할 것을 헤더 밖으로 내보내는 것이라 공통 요소의 소유가 둘로 갈립니다 |
| (다) BLK-0001의 확장을 요청한다 | 슬롯 둘('읽은 시점' TEXT, '새로고침' BOOLEAN)을 더하는 **MINOR** 변경입니다. 2.1.0 → 2.2.0이므로 이미 적어 둔 참조 범위 `^2` 안에 들어옵니다. 블록 ID도 쓴 곳 일곱도 그대로입니다 | **골랐습니다** |

(다)를 골라 **BRQ-0016**을 냈습니다. `reference/` 아래는 한 글자도 고치지 않았습니다.

| 요청 | 무엇을 | 어느 블록에 | 등급 | 더할 슬롯 | props (React prop 이름) | 쓴 곳 |
| --- | --- | --- | --- | --- | --- | --- |
| BRQ-0016 | 슬롯 둘을 더하는 **확장** | BLK-0001 글로벌 헤더 2.1.0 | MINOR (2.2.0 예정) | '읽은 시점'(TEXT), '새로고침'(BOOLEAN) | `readAt`, `onRefresh` | SCR-001-A01 ~ SCR-007-A01 (7곳) |

**BRQ-0001~0015와 성격이 다릅니다.** 그 열다섯은 맞는 블록이 아예 없어 만든 **새 프로젝트
블록**이고, BRQ-0016은 **이미 쓰고 있는 라이브러리 블록을 넓혀 달라는 요청**입니다. 그래서 영역의
`block.id`를 `BRQ-0016`으로 바꾸지 않고 `BLK-0001` `^2` 그대로 두었습니다. 블록은 라이브러리에
실재하고 폐기도 아니므로 QA-07의 판정은 달라지지 않습니다. 다만 **승인되기 전까지 `readAt`과
`onRefresh`는 레지스트리에 없는 이름**이라, 블록 담당자가 등록할 때 이름이 달라지면 헤더를 쓰는
일곱 영역의 props를 함께 고쳐야 합니다(POL-026). 11절에 넘깁니다.

읽은 시점과 새로고침이 걸린 정책은 POL-004이며, 그 영역들이 이미 POL-004를 걸고 있어 **연결을
새로 더하지 않았습니다.** 요구사항도 REQ-020(표시 내용과 저장소 파일의 일치)이 이미 걸려 있습니다.

BLK-0020은 `code.connected`가 `false`라 React prop 이름 대응표가 없습니다. 2026-11-26 결정대로
**코드 연결이 없는 블록은 그대로 쓰고** 와이어프레임용 컴포넌트를 따로 만들지 않았습니다. props
이름(`tabs`, `activeTabId`, `onTabChange`)은 슬롯(탭 목록·활성 표시·콘텐츠 영역)에 맞춰 **제안한
것**이며, 블록 생성자가 code connect를 등록할 때 확정합니다(11절에 넘깁니다).

#### 알림 줄을 두 블록으로 가른 근거

0.1.0에서는 두 줄이 `tone`과 문구만 다르다고 보아 한 블록(BRQ-0005)을 A02와 A07이 함께 썼습니다.
2026-11-26 사람의 검토에서 **한 블록으로 묶지 않기로 정해** 둘로 갈랐습니다. 쓰임이 이렇게
다릅니다.

| 가르는 기준 | BRQ-0005 대기 알림 줄 (A02) | BRQ-0006 변경 영향 알림 줄 (A07) |
| --- | --- | --- |
| 무엇을 알리는가 | 지금 **사람이 해야 할 일**(확정 대기·승인 대기·선택 대기) | 승인된 항목이 **바뀌었다는 사실**. 할 일이 아닙니다 |
| 누르면 어디로 가는가 | **뷰어 바깥**. GitHub PR이나 claude.ai 세션을 새 탭으로 엽니다. 화면은 그대로 남습니다 | **뷰어 안**. 변경 영향(SCR-007)으로 화면을 옮깁니다 |

묶으면 어느 쪽에도 안 쓰는 prop이 절반씩 남습니다. 그래서 블록을 둘로 둡니다.

#### BRQ-0008을 영역 셋이 함께 쓰는 근거

WU-001의 검토에서 **쓰임이 다르면 번호를 공유하지 말라**고 정했습니다. 반대로 쓰임이 같으면
재사용하는 것이 맞습니다. BRQ-0008은 SCR-003-A04와 SCR-004-A04가 함께 쓰고, WU-003에서
SCR-005-A05가 더해졌습니다. 가르는 기준을 BRQ-0005·BRQ-0006 때와 똑같이 대어 보았더니 세 자리의
모든 칸이 같았습니다.

| 가르는 기준 | SCR-003-A04 항목 참조 패널 | SCR-004-A04 분기 정책 목록 | SCR-005-A05 영역 요구사항·정책 목록 |

'걸린 정책이 없습니다'로 둡니다. 문구는 값이지 prop이 아니라 블록을 가를 까닭이 되지 않습니다.
