# 정보 구조도: UX AI Studio

> **IA Agent가 만든 초안입니다. 사람의 승인 전입니다.**
> 승인은 사람이 PR을 병합할 때만 일어납니다(POL-002). 6절의 작업 단위는 **제안**이며,
> 이 문서가 승인되어야 화면설계서 작성의 선택지가 됩니다(POL-037).

## 1. 문서 개요

이 문서는 뷰어의 화면 목록과 화면 사이의 이동, 그리고 화면설계서를 작성하는 작업 단위를 적습니다.
[유저 플로우](USER-FLOW.md)와 [워크 플로우](WORKFLOW.md)에서 뽑았으며, 플로우에 나오지 않는
화면은 만들지 않았습니다.

| 항목 | 내용 |
| --- | --- |
| 상태 | 검토 필요 |
| ID 규칙 | 화면은 `SCR-000`, 작업 단위는 `WU-000`. 1번부터 차례로 붙이고 비는 번호를 두지 않습니다. 한 번 붙인 ID는 바꾸거나 재사용하지 않습니다. |
| 선행 문서 | [유저 플로우](USER-FLOW.md) 0.4.0, [워크 플로우](WORKFLOW.md) 0.3.0, [요구사항 정의서](PRD.md) |
| 화면 수 | 7개 |
| 작업 단위 수 | 4개 |
| 처리용 데이터 | [ia.json](ia.json) |

화면을 뽑은 기준은 하나입니다. **유저 플로우의 단계가 실제로 일어나는 자리**입니다. 단계 42개 중
화면이 필요한 29개(진입 3, 선택 22, 완료 4)를 모아 보니 7개 자리로 모였습니다(5절).

0.2.0과 0.3.0에서 화면을 더하지도 지우지도 않았습니다. 유저 플로우가 0.3.0에서 여섯
(UF-036~041), 0.4.0에서 하나(UF-042)를 더했지만 **일곱 모두 이미 있는 화면에서 일어나는 일**이라
새 화면이 생기지 않았습니다. 바뀐 것은 화면 간 이동(3절)과 단계·화면 배정표(5절)입니다.

이 프로젝트는 시스템의 파일럿이라 저장소의 [정보 구조도](../../docs/06-information-architecture.md)가
같은 뷰어를 `STU-00`으로 이미 설계해 두었습니다. 화면의 덩어리는 그것과 같고, ID 체계만 다릅니다.
설계 대상 서비스의 화면은 `SCR`, 이 시스템 자체의 화면은 `STU`입니다([데이터 규격](../../docs/08-data-spec.md) 3절).

### 메뉴에 대하여

`menu`와 `group`은 **화면을 묶어 부르는 이름일 뿐 새로 만든 내비게이션 계층이 아닙니다.**
플로우에 없는 메뉴 계층을 지어내지 않았습니다. 모든 화면은 프로젝트 목록(SCR-001) →
진행 현황(SCR-002)을 거쳐 들어갑니다(POL-008, POL-006). 진행 현황이 유일한 허브입니다.

```
프로젝트 목록 (SCR-001)
└─ 프로젝트 진행 현황 (SCR-002)        ← 산출물을 고르는 허브
   ├─ 문서 보기 (SCR-003)
   ├─ 플로우 미리보기 (SCR-004)
   ├─ 화면설계서 뷰어 (SCR-005)
   ├─ 검증 결과 (SCR-006)
   └─ 변경 영향 (SCR-007)
```

## 3. 화면 간 이동

### 0.2.0에서 더한 되돌아가기 넷

SCR-003·SCR-004·SCR-005·SCR-007의 머리에 있는 뒤로가기는 화면설계서가 이미 그렸는데
(`SCR-00n-A01`의 인터랙션 '뒤로가기를 누른다') `transitions`에 없었습니다. 검증 보고서 6절의
QA-04가 이 넷을 실패로 짚었습니다. **화면은 그대로 두고 정보 구조도를 화면에 맞췄습니다.**

0.1.0에서는 7절에 "플로우에 그 단계가 없습니다"로 넘겨 두었던 자리입니다. 유저 플로우 0.3.0이
UF-038~041을 세워 근거가 생겼으므로 넷을 그대로 받습니다. 넷을 하나로 묶지 않은 것은 플로우가
넷으로 둔 것을 따른 것입니다(유저 플로우 3.7절). 돌아가 닿는 곳은 넷 다 UF-006(진행 현황에서
일곱 단계의 상태를 본다)입니다.

### 0.3.0에서 더한 되돌아가기 하나

SCR-006의 머리에도 뒤로가기가 있습니다(`SCR-006-A01`의 인터랙션 '뒤로가기를 누른다'). 0.2.0에서는
**대응 단계가 없어 더하지 않고** 7절에 "UF-042가 서면 `trigger` 하나를 더한다"로 넘겼습니다.
유저 플로우 0.4.0이 UF-042('검증 결과에서 진행 현황으로 돌아간다')를 세워 조건이 채워졌으므로
**적어 두었던 대로 더했습니다.** 이동은 20개에서 21개가 되었습니다.

`SCR-006 → SCR-002`가 표에 두 줄인 것은 **까닭이 다른 두 길**이기 때문입니다. 위의 줄은 검증을
아직 돌리지 않아 뷰어가 돌려보내는 길(UF-025의 '결과 없음' 갈래)이고, 새로 더한 줄은 사용자가
머리를 눌러 떠나는 길(UF-042)입니다. UF-042의 디스크립션도 둘을 다른 길로 갈라 적었습니다.
`transitions`는 `trigger` 단위로 적는 자리라 둘을 묶지 않았습니다. 다른 화면 넷(SCR-003·004·
005·007)의 되돌아가기와 같은 모양입니다.

### 0.2.0에서 근거를 바로잡은 넷

이동 자체는 0.1.0에 있었고 **근거만 틀렸거나 비어 있던 것**입니다. 이동을 더하거나 지우지
않았습니다.

| 이동 | 0.1.0의 근거 | 0.2.0의 근거 | 무엇이 틀렸는가 |
| --- | --- | --- | --- |
| SCR-002 → SCR-001 | 제안 (POL-008) | UF-037 → UF-005 | 플로우에 단계가 없어 제안으로 두었습니다. 유저 플로우 0.3.0의 UF-037('프로젝트 목록으로 돌아가 다른 프로젝트를 본다')이 그 단계이므로 **제안 표기를 거둡니다.** |

| SCR-007 → SCR-003 | 제안 (POL-010, REQ-014) | UF-027 '영향받는 항목을 누른다' → UF-012 | **0.1.0이 유저 플로우를 잘못 읽었습니다.** UF-027에는 갈래가 둘 있고 그중 하나가 '영향받는 항목을 눌러 그 항목으로 간다 → UF-012'(POL-019)입니다. UF-012의 화면은 SCR-003이므로 이 이동은 **처음부터 플로우에 있었고 제안이 아닙니다**(QA-03 7번). 7절에 적었던 틀린 서술도 함께 거뒀습니다. |

마지막 줄은 플로우가 아니라 **이 문서가 고칠 것**이었습니다. `user-flow.json`과 `USER-FLOW.md`는
맞으므로 한 글자도 고치지 않았습니다.

## 4. 화면과 요구사항의 대응

**0.2.0에서 표를 넓혔습니다.** 0.1.0의 표는 '화면을 뽑은 근거'만 적어 18개(18/21 = 0.857)에
그쳤고, 화면설계서가 영역에 실제로 건 21개보다 좁았습니다. 검증 보고서 3절이 이 차이를 권고로
남겼고, 화면설계서 11절이 네 작업 단위에서 네 번 "IA Agent가 정할 일"로 넘겼습니다. **정하지
않으면 다음에 화면을 다시 만들 때 같은 차이가 또 쌓이므로 여기서 정합니다.**

| 화면 ID | 화면을 뽑은 근거 요구사항 | 화면설계서가 영역에 더 건 요구사항 |
| --- | --- | --- |
| SCR-001 | REQ-001, REQ-019 | REQ-002, REQ-004, REQ-015, REQ-020 |
| SCR-002 | REQ-002, REQ-003, REQ-004, REQ-005, REQ-020 | REQ-014, REQ-016 |
| SCR-003 | REQ-005, REQ-006 | REQ-004, REQ-015, REQ-020 |
| SCR-004 | REQ-007, REQ-008 | REQ-006, REQ-015, REQ-020, REQ-021 |
| SCR-005 | REQ-009, REQ-010, REQ-011, REQ-012, REQ-017, REQ-018 | REQ-004, REQ-006, REQ-015, REQ-020, REQ-021 |
| SCR-006 | REQ-013 | REQ-004, REQ-006, REQ-011, REQ-014, REQ-016, REQ-018, REQ-020 |
| SCR-007 | REQ-014 | REQ-004, REQ-006, REQ-013, REQ-015, REQ-016, REQ-020 |

두 칸을 합치면 **REQ 21개가 모두 들어갑니다.** 왼쪽 칸만으로는 18개이고, 빠지는 셋은
REQ-015·REQ-016·REQ-021입니다. 오른쪽 칸은 `screens/SCR-00n.json`의 영역 `requirements`를
읽어 온 것이며, 검증 보고서 3절의 표와 같습니다.

### 두 칸을 한 칸으로 합치지 않은 까닭

**정하는 쪽이 다릅니다.** 왼쪽은 "이 화면이 왜 있는가"이고 정보 구조도가 정합니다. 오른쪽은
"요구사항이 어느 영역에서 지켜지는가"이고 화면설계서가 정합니다([데이터 규격](../../docs/08-data-spec.md)
4절의 영역 `requirements`). 합쳐 버리면 화면설계서가 영역을 하나 고칠 때마다 정보 구조도를
따라 고쳐야 하고, **정보 구조도 → 화면설계서라는 방향이 뒤집힙니다.**

그래서 **표는 넓히고 `ia.json`의 `refs`는 넓히지 않았습니다.** `refs`에는 왼쪽 칸의 REQ만
그대로 둡니다. 오른쪽 칸은 읽어 온 값이지 이 문서가 정한 값이 아니기 때문입니다.

### 뷰어 전체에 걸리는 제약 셋

## 5. 유저 플로우 단계의 화면 배정

`user-flow.json`의 `screen`은 **IA Agent가 자기 문서 밖에 쓰는 유일한 자리이며, `screen` 말고
다른 필드는 건드리지 않습니다.** 0.1.0에서 22개를 채웠습니다.

**0.2.0과 0.3.0에서는 `user-flow.json`을 한 글자도 고치지 않았습니다.** 유저 플로우가 0.3.0에서
더한 여섯(UF-036~041)과 0.4.0에서 더한 하나(UF-042)는 모두 이미 있는 화면에서 일어나는 일이라

적었습니다. 새로 배정할 단계도, 새로 만들 화면도 없었습니다.

`step_type`이 진입·선택·완료인 **29개가 모두 채워져 있습니다.** 분기 9개와 이탈 4개는 `null`입니다.

## 6. 작업 단위 (제안)

화면설계서는 작업 단위를 기준으로 작성합니다(POL-035). 아래는 **제안**이며 사람이 이 문서를
승인해야 선택지가 됩니다(POL-037).

묶은 기준은 **사용자가 한 번에 하는 일**입니다. 메뉴 계층이 아니라 유저 플로우의 덩어리를
따랐습니다. 모든 화면이 작업 단위 하나에만 속합니다(POL-036).

| 작업 단위 | 이름 | 속한 화면 | 플로우 구간 | 묶은 근거 |
| --- | --- | --- | --- | --- |
| WU-001 | **프로젝트와 진행 현황** | SCR-001, SCR-002 | UF-001~UF-011, UF-037 | 들어와서 '지금 어디까지 됐나'를 보는 한 묶음. 세 사용자 유형이 모두 이 길로 들어온다(POL-008). 뷰어의 입구이자 다른 모든 화면으로 나가는 허브다. |
| WU-002 | **문서와 플로우 보기** | SCR-003, SCR-004 | UF-012~UF-018, UF-036, UF-038, UF-039 | 생성 결과를 읽고 참조를 따라가는 한 묶음. 두 화면이 서로를 오가며(정책 ID → 문서 항목, 참조 패널 → 다이어그램) 같은 '항목 ID와 참조 이동' 요소를 공유한다. 따로 설계하면 어긋나기 쉽다. |
| WU-003 | **화면설계서 보기** | SCR-005 | UF-019~UF-023, UF-040 | 화면설계서 JSON을 동작하는 화면으로 그리는 유일한 화면이라 혼자 둔다. 영역·블록·인터랙션이라는 구조가 다른 화면과 전혀 다르고, 블록 참조와 등록 요청 표시(POL-016)도 여기에만 있다. |
