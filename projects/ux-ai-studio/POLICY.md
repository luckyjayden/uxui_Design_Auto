# 정책서: UX AI Studio

> **Policy Agent가 만든 초안입니다. 사람의 승인 전입니다.**
> 승인은 사람이 PR을 병합할 때만 일어납니다(POL-002).

## 1. 문서 개요

이 문서는 [요구사항 정의서](PRD.md)의 요구사항마다 지켜야 할 조건·권한·상태값·예외를 정한 것입니다.
어느 요구사항에도 걸리지 않는 정책은 만들지 않았습니다. 정책마다 받드는 `REQ`를 `refs`에 적었습니다.

| 항목 | 내용 |
| --- | --- |
| 상태 | 검토 필요 |
| ID 규칙 | `POL-000`. 1번부터 차례로 붙이고 비는 번호를 두지 않습니다. 한 번 붙인 ID는 바꾸거나 재사용하지 않습니다. |
| 유형 | 서비스, 운영 |
| 참조 | `refs`에 그 정책이 받드는 `REQ-000`을 하나 이상 적습니다. |
| 처리용 데이터 | [policies.json](policies.json) |

정책은 21개입니다. 서비스 19개, 운영 2개입니다.

ERD가 없다는 것을 전제했습니다. 상태와 조건은 이 문서가 맡고, 데이터가 어떻게 흐르는지는 다음 단계의
워크 플로우가 맡습니다.

`exceptions`에 적은 예외는 모두 화면에서 다룰 수 있는 것만 적었습니다. 나중에 Screen Agent가 이 예외를
화면 영역으로 옮겨 적습니다.

### 4.1 문서 상태 다섯의 앞뒤 차례 (POL-005)

한 자리에 상태가 둘 이상 묶일 때 어느 쪽이 뒤처졌는지 가리려면 차례가 있어야 합니다(POL-006).
차례는 이렇습니다.

```
대기 → 수정 필요 → 생성 중 → 검토 필요 → 승인
```

**뒤로 갈수록 승인에 가깝고, 앞에 오는 쪽이 뒤처진 쪽입니다.** 매긴 기준은 **승인까지 남은 일**입니다.

| 상태 | 승인까지 남은 걸음 | 왜 이 자리인가 |
| --- | --- | --- |
| 대기 | 3 (생성 중 → 검토 필요 → 승인) | 아직 아무것도 만들어진 적이 없습니다. 맨 앞입니다. |
| 수정 필요 | 3 (생성 중 → 검토 필요 → 승인) | 다시 만들기를 **아직 시작하지 않은** 상태입니다. 남은 걸음이 '대기'와 같지만 한 번 만들어진 것이 남아 있어 '대기'보다 뒤입니다. |
| 생성 중 | 2 (검토 필요 → 승인) | 이미 만들고 있습니다. 그래서 '수정 필요'보다 **뒤**입니다. |
| 검토 필요 | 1 (승인) | 초안과 PR이 있고 사람의 검토만 남았습니다. |
| 승인 | 0 | 끝난 상태입니다. |

**'수정 필요'가 '생성 중'보다 앞인 까닭**이 이 차례의 핵심입니다. '수정 필요'는 승인 뒤에
참조하던 항목이 바뀌어 **다시 만들어야 하는** 상태이고, 다음에 일어나는 일은 에이전트를 다시
돌려 '생성 중'이 되는 것입니다. 지금 만들고 있는 문서보다 **할 일이 한 걸음 더 남아 있으므로**
더 뒤처진 쪽입니다. 한 번 만들어졌던 이력이 아니라 **승인까지 남은 일**로 가립니다.

이 차례를 쓰는 곳은 POL-006 하나입니다. 플로우 단계(유저 플로우·워크 플로우 둘)와 화면설계서
단계(작업 단위 여럿)의 단계 배지를 고를 때 씁니다.

차례에 두지 않는 것이 하나 있습니다. **다섯 값에 없는 상태('알 수 없음')는 차례 밖**입니다.
묶인 것 가운데 그런 값이 있으면 뒤처진 쪽을 고르지 않고 그 자리를 '알 수 없음'으로 보입니다
(POL-005, POL-006의 예외).

POL-007의 '승인 대기'와는 **다른 축**입니다. POL-007은 *누구를 기다리는가*를 가르고 이 차례는
*승인까지 얼마나 남았는가*를 가립니다. '검토 필요'와 '수정 필요'가 POL-007에서 함께 '승인 대기'로
묶이는 것과, 이 차례에서 둘의 자리가 떨어져 있는 것은 서로 어긋나지 않습니다.

## 5. 권한

정의서 3절의 사용자 유형을 따릅니다. 뷰어는 읽기 전용이라 권한의 차이는 **무엇을 주로 보는가**까지입니다.
막는 권한은 POL-020 하나뿐입니다.

| 사용자 유형 | 주로 보는 것 |
| --- | --- |
| 기획자 | 진행 현황, 문서와 참조, 플로우, 화면설계서, 검증과 변경 (POL-007, POL-008, POL-013, POL-019) |
| 개발·QA 담당자 | 승인된 화면설계서와 검증 결과, PPTX (POL-014, POL-017, POL-018) |
| UI 블록 담당자 | 화면이 쓴 블록과 등록 요청 (POL-016) |

## 6. 예외 처리

아래 예외는 모두 화면에서 다룰 수 있는 것입니다. Screen Agent가 해당 화면 영역의 예외로 옮겨 적습니다.

| 정책 | 예외 |
| --- | --- |
| POL-001 | 링크의 주소를 만들지 못하면 '연결할 곳이 없습니다'를 보이고 링크를 비활성으로 둔다 |
| POL-002 | 상태가 '검토 필요'인데 PR 번호가 없으면 'PR이 아직 열리지 않았습니다'를 보인다 |
| POL-003 | 아직 파일이 없는 문서는 GitHub 링크 대신 '아직 만들어지지 않았습니다'를 보인다 |
| POL-004 | 파일을 읽지 못하면 그 자리에 경로와 함께 '읽지 못했습니다'를 보이고 나머지는 그대로 보인다 / JSON이 깨져 있으면 그 문서의 항목 목록 자리에만 '읽을 수 없습니다'를 보인다 |
| POL-005 | 상태 파일에 그 문서의 줄이 없으면 '대기'로 보인다 / 다섯 값에 없는 상태는 '알 수 없음'으로 구분한다 / '알 수 없음'은 앞뒤 차례에 두지 않고, 그 상태가 섞인 자리는 뒤처진 쪽을 고르지 않는다 |

## 8. 총괄 에이전트에 넘기는 사항

요구사항 정의서 6절이 넘긴 사항 가운데 정책으로 정하려면 사람의 확정이 필요한 것들입니다.
**제안**으로 적고 정책 본문에도 같은 표시를 두었습니다.

| 사항 | 지금 정한 것 | 왜 확정이 필요한가 |
| --- | --- | --- |
| 저장소 변경이 화면에 반영되는 시점 | POL-004에서 새로고침으로 다시 읽는 것으로 두었습니다 | 실시간이면 읽는 방식과 화면의 상태 표시가 달라집니다 |
| 뷰어가 읽는 저장소의 범위와 열람 권한 | POL-020에서 저장소의 접근 권한을 그대로 따르는 것으로 두었습니다 | 권한을 따로 두면 운영 정책이 하나 더 필요합니다 |
| PPTX 장표 구성 | POL-017에서 화면 한 장에 장표 한 장으로 두었습니다 | 작업 단위나 영역 단위로 나누면 내보내기 정책이 달라집니다 |
| 요구사항 우선순위 기준 | 정책에 우선순위를 두지 않았습니다 | 요구사항의 우선순위가 제안이라 정책으로 옮기지 않았습니다 |

### 8.1 0.2.0에서 정한 것과 담당 에이전트에 넘기는 것

검증 0.2.0의 QA-02 실패(다섯 상태의 앞뒤 차례가 정책에 없음)를 받아 고친 판입니다.

| 넘기는 곳 | 무엇을 | 왜 |
| --- | --- | --- |
| **screen** | `SCR-002-A04` 디스크립션의 차례 한 줄을 **`대기 → 수정 필요 → 생성 중 → 검토 필요 → 승인`**으로 고칩니다. 지금 적힌 `대기 → 생성 중 → 수정 필요 → 검토 필요 → 승인`과 **'수정 필요'와 '생성 중'의 자리가 서로 바뀝니다.** `STORYBOARD.md`에 같은 줄이 더 있습니다 | 화면이 세운 차례와 4.1절이 정한 차례가 다릅니다. 정하는 자리는 정책이라 정책을 기준으로 맞춥니다 |
| **screen** | 같은 디스크립션의 "POL-005의 다섯 값을 '…' 순으로 보고"는 **그대로 두어도 맞습니다.** 차례가 이제 POL-005에 있습니다. 디스크립션에 적은 보기("유저 플로우가 '승인'이고 워크 플로우가 '검토 필요'이면 배지는 '검토 필요'")도 바뀐 차례에서 그대로 맞습니다 | 고칠 곳은 차례를 적은 한 줄뿐입니다 |
| **screen** | `SCR-002-A04`가 "화면설계서 단계는 가장 뒤처진 작업 단위의 상태를 보인다"고 적은 것은 이제 POL-006의 조건이 됐습니다. 근거를 POL-006으로 적어 두면 됩니다 | 0.1.0의 POL-006은 플로우 단계만 적어 화면이 혼자 넓혀 쓰고 있었습니다 |
| **flow** | 머리의 뒤로가기는 **POL-006(산출물 보기 → 진행 현황)과 POL-008(진행 현황 → 프로젝트 목록)의 조건**이 됐습니다. UF-037~041이 건 근거를 바꾸지 않아도 되고, 새로 세울 UF-042(SCR-006의 뒤로가기)도 **POL-006**을 그대로 걸면 됩니다 | 유저 플로우 9절이 "되돌아갈 수 있다는 것 자체를 정한 정책이 없다"고 넘긴 것에 대한 답입니다 |

**되돌아가기를 새 정책(POL-022)으로 세우지 않았습니다.** 까닭은 셋입니다.
(1) 되돌아가는 곳이 **프로젝트 목록과 진행 현황 둘뿐**이고 그 둘이 각각 POL-008·POL-006이
"고르는 자리는 여기 하나"라고 이미 정하고 있어, 돌아오는 길은 같은 정책의 뒷면입니다.
(2) 새 ID를 세우면 유저 플로우·워크 플로우·화면 영역 **셋 모두**가 그것을 참조해야 하고
(QA-02는 어디에서도 참조하지 않는 POL을 실패로 봅니다), 그렇지 않으면 고아 정책이 하나 생깁니다.
(3) 고치는 항목을 적게 두라는 지시가 있었습니다. 조건 두 줄로 같은 것을 정할 수 있습니다.

> 새 정책이 필요해지면 다음 번호는 **POL-022**입니다. 이 프로젝트의 정책은 POL-001~021
> 스물하나입니다(POL-040이 아닙니다).
